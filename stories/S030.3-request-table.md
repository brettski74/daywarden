# User Voice

As a parent, I want to see each request a child's computer made, when it started and ended, how much it sent and
received, and whether a rule refused it, both by drilling into a host on the usage graph and on a page of its own, so
that I can see exactly what was fetched and what was blocked.

# Behaviour

## The request table

The drill-down and the Requests page show the same table.

- The columns are Start, End, Duration, Address, Client group, Site group, Quotas, Method, Host, Path, Query, Status,
  Type, Down, Up, and Outcome.
- [ ] Start is when the proxy received the request. End is when the response finished, the transfer was cut, or it
  failed. A request still running when the table was opened has no End, and its Duration is the time so far.
- [ ] Address is the IP address of the computer that sent the request. Host follows the rule in S030.2.
- [ ] Path is the address without its query string, such as `https://www.youtube.com/watch`, and Query is the query
  string without its `?`, such as `v=abc123&t=42`. Pointing at Path shows the full address.
- [ ] Down and Up are the body bytes received and sent, as the ledger counts them. Status is the HTTP status the browser
  received, and Type is the response's content type, such as `video/mp4`.
- [ ] Outcome is allowed, denied, redirected, or cut. A denied or redirected request is listed with the status the
  browser received, 403 or 302, and no bytes. Quotas names the quotas that accepted the request's bytes.
- [ ] Clicking a column heading sorts the table by that column, ascending, and clicking it again sorts descending. An
  arrow beside the heading shows the sort. Headings are buttons, so Enter and Space sort too. The default is Start,
  newest first.
- [ ] The table shows 100 requests a page, with Previous and Next links, and the status bar says which, such as
  `Requests 101 to 200 of 4,213.` Sorting covers every request, not only the page on show.
- [ ] The sort and the page are in the page address, so Reload, Back, and a bookmark open the same table.
- [ ] Column headings stay in view while the rows scroll, as every portal list's do.

## Drill-down from a host

- [ ] Double-clicking a host's bar in the S030.2 bar chart, or pressing Enter on it, opens the table beneath the bar
  chart with the shared expand animation. Its heading names the line, the host, and the range, such as
  `younger, www.youtube.com, Past week: requests`. It lists every request to that host within the line's group, the
  filters, and the range.
- [ ] The host drilled into is in the page address. Double-clicking another bar replaces the table. A close button
  collapses it. Changing a filter, the range, or the line drilled into closes it.

## Requests page

- [ ] The Usage group in the sidebar gains Requests, beneath Minutes and Bytes, which opens `/parent/usage/requests`.
- [ ] The page shows the table for every request within its filters. It has the Client groups, Site groups, Quotas, and
  Date range of S030.1, with the same rules, and no Group by.
- [ ] A Host box lists only requests whose host contains what is typed, such as `googlevideo`, which matches every
  `rr3---sn-ab5l6nrz.googlevideo.com`. An Outcome pull-down chooses any of allowed, denied, redirected, and cut, so
  choosing denied and redirected lists what rules refused. With nothing chosen, every outcome is listed.
- [ ] The presets of S030.1 work here as on the graph pages, including Default and an address that names a preset. A
  preset's Group by is ignored on this page, and the Host box and Outcome are not part of a preset.
- [ ] Every filter is in the page address with the sort and the page. Changing a filter returns to the first page.

## Retention

- [ ] `request_retention` in the policy file sets how long requests are kept, with the same form, default, load error,
  and hourly deletion as `host_retention` in S030.2. The table never lists an older request. A range that starts
  before the oldest request kept says from when requests are kept, such as
  `Requests are kept for 30 days, from Wednesday 14 October 2026.`

# Notes

## Design hints

- **One row per request, keyed by the proxy's flow id.** The decisions service already receives the flow id, the client
  address, the method, and the URL for every request, and decides it. It inserts the row there, with the start time,
  the client group, the site group, and the outcome, so a refused request is recorded too. The observations service
  adds the bytes each way and the quotas as reports arrive, as a separate table of request and quota pairs. Both
  services already share `policy.sqlite3`.
- **The proxy.** It sends one more report when each forwarded flow ends, even with no bytes left to report, carrying
  the status, the content type, and that the flow has ended. A cut or a failure ends it too. A denied or redirected
  request gets its status from the decision, because the proxy makes that answer itself.
- **Path, Query, and Host** are split from the URL when the row is written, and the full URL is kept as well.
- **One endpoint** serves both the drill-down and the page. It takes the filters, an exact host for the drill-down or a
  host fragment for the page, the outcomes, the sort, and the page number.
- **Size.** A busy page can make a hundred requests, and video streams many more. At about 20,000 requests a day for a
  client group, 30 days is around 600,000 rows. Index by client group, host, and start time so a drill-down stays a
  range scan. The Requests page sorts across every matching row, so it may need an index on start time alone.
- Full URLs can carry sign-in tokens and search terms. They stay in the `policy-data` volume and are shown only to a
  signed-in parent.

## Out of scope

- Downloading the requests. The raw data download is a later story.
- Request and response headers, and request bodies.
- Searching the Path or Query columns.

## Sizing

21 points: the end-of-flow report from the proxy, the request rows written by two services, the request retention,
the endpoint with filtering, sorting, and paging across every request, the table with its sort headings and page links,
and the Requests page, which reuses the S030.1 filters and presets.
