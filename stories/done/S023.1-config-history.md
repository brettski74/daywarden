Ticket: S023.1
Title: Keep a history of the config directory in git
Status: Done
Story Points: 5
Last Updated: 2026-11-08 22:30:00
---

# User Voice

As a parent, I want every change to the policy files kept in a local git history, so that when I, or the parent
portal, save something dumb, I can get the previous version back.

# Use Cases

## UC1 - The history is created

- `install.sh`, `make up`, and `dw up` create a git repository in the config directory when it has none, and commit
  what is there as the first version. On an installed machine, that is `~/daywarden/config`.
- The repository is local. It has no remote, and nothing is pushed anywhere.
- It ignores editor leftovers, such as `*~`, `*.swp`, and `.#*`, and the `*.sample` files the installer writes,
  through a `.gitignore` it creates. The samples are not read by anything, and each install rewrites them. Everything
  else in the config directory is committed, including `policy.yaml`, `bypass.txt`, and included policy files.
- A config directory that is already inside another git work tree, such as `config/` in a clone of the daywarden
  repository, gets no repository of its own. The outer repository is its history. `dw up` says so in one line.
- Installing a new version keeps the existing history. The new `.sample` files it writes make no commit.

## UC2 - Hand edits are committed when they are applied

- After a successful `dw reload` or `dw up`, any uncommitted change in the config directory is committed. The message
  is the household-local time, the host user who ran it, and the command, such as
  `2026-11-08 21:15 -0500 blg: dw reload`. The commit author is that user.
- A `dw reload` or `dw up` that fails its policy check commits nothing, so a broken edit never becomes a version.
- `dw check` never commits.
- When the commit fails, for example because the disk is full, the reload still applies. `dw` prints a warning that
  the change is not in the history, and why.

## UC3 - Getting an old version back

- The README's new section on the config history shows the steps: `git log` in the config directory to find the
  version, `git show <version>:policy.yaml` to read it, `git checkout <version> -- policy.yaml` to restore it, and
  `dw reload` to apply it. That reload commits the restored file as a new version, so nothing in the history is lost.

# Acceptance Criteria

- [x] After a fresh install, `git log` in `~/daywarden/config` shows one commit holding `policy.yaml`, `bypass.txt`,
      and `.gitignore`, and no `.sample` file. `git status` is clean.
- [x] Installing a new version that brings a changed `policy.yaml.sample` adds no commit, and `git status` stays
      clean.
- [x] Editing `policy.yaml` by hand and running `dw reload` adds a commit whose message has the time, the user who ran
      it, and `dw reload`. `git show` on that commit shows exactly the edit.
- [x] A broken edit, such as an unknown client group, makes `dw reload` fail, and `git status` still shows the edit
      as uncommitted. Fixing it and running `dw reload` again commits the fixed version.
- [x] `dw check` with an uncommitted edit leaves it uncommitted.
- [x] `dw reload` with nothing changed adds no commit.
- [x] An edit to `bypass.txt` is committed by the next `dw reload` or `dw up`.
- [x] Restoring an older `policy.yaml` with `git checkout <version> -- policy.yaml` and running `dw reload` applies it
      and adds a new commit. The later versions are still in `git log`.
- [x] Installing a new version over an existing install keeps the old commits.
- [x] `make up` in a clone of the daywarden repository creates no `config/.git`, and `git status` in the clone shows
      nothing new.
- [x] Removing `.git` from `~/daywarden/config` and running `dw up` starts a new history with the current files as
      its first commit.
- [x] An editor backup file, such as `policy.yaml~`, is never committed.
- [x] On a machine where the host user has never set `git config user.name` or `user.email`, the install and
      `dw reload` commit without asking anything. `git log --format='%an <%ae> %cn <%ce>'` shows the host login at
      `daywarden.invalid` as both author and committer. `git config --global --list` is unchanged afterwards.
- [x] The repository and every file in it are owned by the host user who installed daywarden, so `git log`,
      `git checkout`, and hand edits work without `sudo`.

# Notes

Depends on S014 and S016. This story covers the history, and the commits made by the installer and `dw`. S023.2 adds
the commits made by the parent portal's saves, and how a save treats hand edits it finds.

- Host-side commits are made by `dw`, which runs as the host user, so ownership is right without any work. `git`
  becomes one of the host tools `install.sh` checks for.
- S023.2's portal saves commit from inside the decisions container, which needs `git` in the image, or a pure-Python
  git library. Both writers use git's own index lock. A commit that finds the lock taken waits briefly and then
  reports the failure as in UC2.
- Commits never depend on anyone's git setup, and nothing asks for an identity. `--author` alone is not enough: with
  no `user.name` and `user.email` configured, git still refuses with "Committer identity unknown". Every commit sets
  both the author and the committer for that one command, through `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`,
  `GIT_COMMITTER_NAME`, and `GIT_COMMITTER_EMAIL`, or `git -c user.name=... -c user.email=...`. Nothing is written to
  the host user's global git config or to the repository's config.
- The name is the person: the host login for `dw` and the installer, and the parent's username for a portal save
  (S023.2). The email is that name at `daywarden.invalid`, such as `blg@daywarden.invalid`. `.invalid` is reserved and
  never delivers, which suits a repository that is never pushed. Parent accounts gain no display name or email for
  this.
- The data directory is not part of this history. Spelling recordings are audio files under `~/daywarden/data`. The
  attic from S023.2 is what protects a retired word.

## Files Changed

- `bin/daywarden-lib.sh`: `dw_history_keep` creates the history, or commits when there is one. `dw_history_commit`
  commits any change. `dw_git` runs git with the user's global and system git config ignored, and the author and
  committer set to the host user at `daywarden.invalid`. `dw_household_tz` reads `timezone:` from `policy.yaml` for the
  commit time.
- `bin/dw`: `up` and `restart` keep the history once every service is healthy. `reload` commits once the decisions
  service has the new policy. The observations and autoconfig steps of `reload` moved into `reload_others`. The usage
  mentions the history.
- `deploy/install.sh`: `git` is a required tool. A config directory with no `.git` gets a history after the config
  files are laid out.
- `tests/hostfakes.py`: real `git` is on the fake host's `PATH`, and `without=` can leave out a real tool.
- `tests/test_make_targets.py`: `make up` in a git checkout makes no `config/.git` and leaves `git status` clean.
- `README.md`: a new Config history section with the restore steps, `git` in the installer's requirements, and
  `config/.git` in the install layout.

## Change Summary

`~/daywarden/config` is now a local git repository with no remote. `install.sh` creates it when there is none, with a
`.gitignore` that leaves out `*~`, `*.swp`, `*.swo`, `.#*`, `#*#`, and `*.sample`, and commits what is there as the
first version, with the message `<time> <user>: install.sh`. An upgrade over an existing history leaves it alone, so the
new `.sample` files make no commit. An upgrade over an install from before this story starts the history.

`dw up` and `dw restart` create the history when `.git` is missing, or commit any uncommitted change, after the stack is
healthy. `dw reload` commits once the decisions service has accepted the policy. If observations or autoconfig then fail,
the commit is still made, because the policy is in use. A failed policy check commits nothing, and `dw check` never
commits. When something is committed, `dw` prints `Saved in the config history: <files>.` The commit time is in the
household timezone from `policy.yaml`, or the machine's when it sets none.

Every git call sets `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1`, and the author and committer through the
`GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables. A machine with no git identity commits without asking. A user whose
`~/.gitconfig` turns on commit signing or a global hooks path is not affected either. Nothing is written to any git
config. A commit that finds `index.lock` waits up to 5 seconds. A commit that fails, for example a full disk, prints a
warning naming the reason, and the reload still applies and exits 0.

A config directory inside another git work tree, such as `config/` in a clone, gets no history of its own. `dw up` and
`dw restart` say so in one line, and `dw reload` commits nothing there.

Two choices go beyond the story's wording. `dw restart` keeps the history as `dw up` does, because it applies the policy
the same way and is what an upgrade runs. The start at boot does not commit, so a reboot never makes a version.

## Suggested Acceptance Testing

### Acceptance test cases for S023.1

1. Build a package with `make dist` and install it on a machine, or for a fresh `HOME`, with no `~/daywarden`. In
   `~/daywarden/config`, `git log --stat` shows one commit, `<date> <time> <offset> <you>: install.sh`, holding
   `.gitignore`, `bypass.txt`, and `policy.yaml`, with no `.sample` file. `git status` is clean, and `git remote` prints
   nothing.
2. Add a comment to `policy.yaml` and run `dw reload`. It prints `Saved in the config history: policy.yaml.`
   `git log -1` shows a message with the time in the household timezone, your login, and `dw reload`. `git show` on it
   shows exactly the added line.
3. Change a rule's client group in `policy.yaml` to one that does not exist and run `dw reload`. It fails with the
   error, and `git status` still shows `policy.yaml` modified. Fix it and run `dw reload` again. The fixed version is
   committed and `git status` is clean.
4. Make an edit, then run `git checkout <the first commit> -- policy.yaml` and `dw reload`. The old file is applied, a
   new commit is added, and the commits in between are still in `git log`.
5. Edit `policy.yaml` and run `dw check`. `git status` still shows the edit, and no commit is added.
6. Run `dw reload` with nothing changed. No commit is added, and nothing about the history is printed.
7. Add a line to `bypass.txt` and run `dw up` (or `dw restart`). The change is committed with `dw up` (or
   `dw restart`) in the message.
8. Open `policy.yaml` in vim and save, leaving `policy.yaml~` or `.policy.yaml.swp` behind, then run `dw reload`.
   `git ls-files` lists no backup or swap file, and `git status` is clean.
9. On a user with no `user.name` or `user.email` (`git config --global --list` shows neither), install and run
   `dw reload` after an edit. Nothing asks for a name. `git log --format='%an <%ae> %cn <%ce>'` shows
   `<login> <<login>@daywarden.invalid>` for both. `git config --global --list` is the same as before.
10. Install a newer package over this one, with a changed `config/policy.yaml` in the package. `policy.yaml.sample`
    changes, `git log` keeps every earlier commit, no commit is added, and `git status` is clean.
11. Remove `~/daywarden/config/.git` and run `dw up`. It prints `Started the config history in ~/daywarden/config.`,
    and `git log` shows one commit, `... dw up`, holding the current files.
12. In a clone of the daywarden repository, run `make up`. It says `config` is inside the clone's git repository.
    There is no `config/.git`, and `git status` in the clone shows nothing new.
13. Run `ls -la ~/daywarden/config ~/daywarden/config/.git`. Everything is owned by the user who installed, and
    `git log`, `git checkout`, and editing work without `sudo`.
14. Make `~/daywarden/config/.git/objects` read-only (`chmod -R a-w`), edit `policy.yaml`, and run `dw reload`. The
    reload applies and exits 0, with a warning that the change is not in the config history and git's reason. Restore
    the permissions, and the next `dw reload` commits the edit.
15. On a machine without `git`, run `install.sh`. It stops with `git is not installed.` and
    `Fix: sudo pacman -S git`, and changes nothing.
