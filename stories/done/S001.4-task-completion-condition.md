# User Voice

As a parent, I want entertainment sites to stay redirected until today's revision tasks are finished, so that YouTube comes after schoolwork.

# Use Cases

- A rule condition `tasks_complete` carries a required count, with an optional different count for named weekdays.
- The condition is true when the number of successful revision completions for this client on this local day is greater than or equal to the count that applies today.
- Until S003 records real completions, the count is whatever is stored for that client and day, including a count written by a test or by an administrator.

# Acceptance Criteria

- [x] A required count of 2 is false when the stored count is 0 or 1, and true when it is 2 or more.
- [x] A Wednesday override of 1 is used on Wednesday. The default of 2 is used on Thursday when Thursday has no override.
- [x] The count is per client. Another client's completions do not change this client's result.
- [x] The count resets when the household date changes. A completion stored for yesterday does not count today.
- [x] Plugged into the sample schedule from S001.3, a stored count of 2 at 16:00 on Wednesday makes rule 4 continue, and a stored count of 1 at the same time redirects.
- [x] The condition does not care which task types made up the count. That catalogue arrives in S003.

## Change Summary

A `tasks_complete` rule now carries `required`, a whole number of zero or more. It is true when the successes stored for this client on the household-local date are at least the count that applies that day. A `[[groups.rules.weekdays]]` table sets a different count for one named weekday. Thursday with no row keeps `required`. The same weekday twice is rejected, and any other condition that is given a count is rejected. The boolean `tasks_complete` argument on `evaluate` and `decide` is gone. Callers pass `completed`, which defaults to zero. `quota_remaining` is still that boolean, and it still defaults to remaining, so the Wednesday schedule at 16:00 allows once the stored count reaches 2 and redirects while it is 1.

The count is one number. It has no task type. S003 will be the thing that writes it from real successes. Until then `PolicyStore.set_task_completions(client_id, day, count)` replaces the stored number, and `task_completions` reads it. A missing row is zero. An IP that is not a client is zero. The day is the household-local date of the request, so a count stored for yesterday is not read today, and the date rolls at household midnight rather than UTC midnight. Reloading the policy file keeps the count, because the client keeps its id. Removing the client drops the count. The service holds its database connection open and reads it on every decision, so a count written by another connection is used on the next request without a restart.

The rows live in schema version 4, in `task_completions` and `rule_weekday_counts`, plus a `required` column on `rules`. A version-3 database gains those and keeps its rules. A `tasks_complete` rule left over from before this column existed has no required count, and the condition stays false until the file is loaded again with one.

## Suggested Acceptance Testing

- Run `python -m pytest tests/test_policy_tasks.py tests/test_policy_rules.py tests/test_policy_decisions.py tests/test_policy_groups.py`. No Docker is needed. These cover the 0/1/2/3 threshold, the Wednesday override against Thursday, per-client counts, the household midnight boundary, the Wednesday 16:00 schedule with a stored 2 and a stored 1, invalid rules, the SQLite round trip, a second connection seeing a write, and a version-3 database upgrade.
- Rebuild the decisions image, then run `python -m pytest tests/test_policy_service.py`. It posts the same Wednesday 16:00 request after writing a count of 2 and again after writing 1. The image is what the container runs, so a code change is invisible until that rebuild.
- On the real stack, give a group a `tasks_complete` rule with `required = 2`, set `household.revision_task` if the false branch uses that token, and `docker compose up -d --build decisions`. A request that reaches the rule should redirect while the count is 0. `docker compose logs decisions` should still show the group and its rules.
- Write a count without restarting. Use the household-local date, not the container's UTC date. The decision log line shows that time. A count of 2 should let the following rule run (allow, while quota is still assumed remaining). A count of 1 should redirect again.

  ```sh
  docker compose exec -T decisions python - <<'PY'
  from datetime import date
  from policy.store import PolicyStore
  store = PolicyStore("/var/lib/smartproxy/policy.sqlite3")
  (client_id,) = store.connection.execute(
      "SELECT id FROM clients WHERE name = ?", ("Younger child",)
  ).fetchone()
  store.set_task_completions(client_id, date.fromisoformat("2026-10-21"), 2)
  store.close()
  PY
  ```
- Store 2 for yesterday's household date and leave today at 0. Today's request should still redirect.
- Give the other client a count of 2 and leave this client at 1. This client's request should still redirect.
- Add `[[groups.rules.weekdays]]` with `day = "wednesday"` and `required = 1`, restart, and store 1. Wednesday should continue and Thursday should redirect.
- Leave `required` off a `tasks_complete` rule. The decisions service should fail to start, and `docker compose logs decisions` should say it needs a required count.
- An existing `policy-data` volume from schema 3 should migrate on restart. The log should show the stored policy loading, not a schema error.
