# User Voice

As a parent, I want to rename a client group, site group, time window, quota, or rule set, and keep its usage and
attempt history, so that a name chosen in a hurry does not stay forever or split the graphs in two.

# Behaviour

## Renaming

- [ ] Each saved item on the S007.2 pages has Rename, and a rule set's page from S007.5 has Rename beside Save. Rename
      opens a `NameDialog` and renames at once. It is not part of the next save, and it is disabled while the page
      has unsaved changes, with a title that says why.
- [ ] A rename changes the item's key and every reference to it in every policy file, in one commit, such as
      `2026-11-18 21:15 -0500 brett: renamed client group younger to kids`. References include rules and inline
      rules, a quota's `ruleset`, `entry`, and the `group` or `groups` of each task in `tasks.d`. Comments and layout
      elsewhere are kept.
- [ ] Renaming the rule set that `entry` names, or a time window several rules use, leaves every decision the same as
      before.
- [ ] A name already used in that namespace, `default` for a client or site group, and a name the loader refuses keep
      the dialog open with the reason. A rename that changes only case is allowed.
- [ ] A name that a client group, site group, or quota no longer in the policy left history under is refused, and the
      reason says history is still stored under it. A merge of two histories is never made by a rename.
- [ ] If any step fails, every file and every stored row is put back, and the status bar gives the reason.

## History

- [ ] After `younger` is renamed to `kids`, the usage graph shows one `kids` line over the whole range, with no
      `younger` line. Attempts, task trends, the arithmetic facts page, and spelling word statistics show the earlier
      attempts under `kids`. Today's score and the tasks required today are the same as before the rename.
- [ ] After the `entertainment` quota is renamed to `fun` on a day when 40 of 45 minutes are used, entertainment
      sites close after 5 more minutes, not 45. The usage graph shows the quota's earlier days under `fun`.
- [ ] After a site group is renamed, the usage graph, the host drill-down, and the request table show its earlier
      traffic under the new name.
- [ ] A download running across a rename is not cut by the rename, and its later usage counts under the new names.
- [ ] A saved usage preset that named the old group or quota names the new one.

# Notes

Depends on S007.2 and S007.5. This changes stored household data, so it is a story of its own, as AGENTS.md asks.

Rows to move, in one transaction: for a client group, `attempts`, `parent_checks`, `task_turns`, the arithmetic fact
and spelling word figures, `group_buckets`, `quota_buckets`, `host_buckets`, `host_quota_buckets`, `requests`, and
`transfers`. For a site group, the usage, host, request, and transfer rows. For a quota, `quota_buckets`,
`host_quota_buckets`, `request_quotas`, and the ceilings in `transfers`. Also `usage_presets`. Time windows and rule
sets have no stored history. The decision log keeps the old names as it wrote them.

Reload the services after the rows have moved and before the commit, so an observation that arrives after the reload
files under the new name. An observation that arrives between the move and the reload may still file under the old
name. Moving those rows once more after the reload closes that gap. Take back the file edits and the moved rows
together, as a task rename does in S027.

No MCP rename tools. S036.3's answer still stands for agents: a new name is a delete and a create.

Sized at 8: one reference rewrite on the existing YAML editor, and a transaction over about a dozen tables, each
tested through the page that reads it.

# Implementation

## Files Added

- `policy/policy_rename.py`: `renamed_text`, which changes an item's key and every scalar in one file that names it, keeping the rest of the text.
- `policy/rename_history.py`: the tables and columns that file rows under a client group, site group, or quota, `move` in one transaction, and `stored_names` for the refusal.
- `tests/test_policy_rename.py`: the rename through the portal's data address, with the files, the stored rows, the presets, open transfers, and every take-back.

## Files Changed

- `policy/policy_admin.py`: `PolicyChanges.rename` and `rename_page`, and `_write` takes extra steps and a step to run after the reload.
- `policy/task_admin.py`: `change` takes `after_reload`. A failure there takes every step back and reloads again.
- `policy/hierarchy.py`: `Written.files`, every policy file that was read, which is where references are looked for.
- `policy/portal.py`: `POST /parent/api/policy/<page>/rename`.
- `policy/portal/src/pages/Policy.tsx`, `pages/RuleSets.tsx`, `components/NameDialog.tsx`: `RenameButton` on each saved item and on a rule set's page, and `NameDialog` starts with the old name selected.
- `policy/portal/src/policy.test.tsx`, `ruleSets.test.tsx`: the button, the dialog, and the refusals.
- `docs/parent-portal.md`: Rename on the policy pages.

## Change Summary

A rename is one `TaskAdmin.change`, as a task rename is in S027: the whole policy is checked with the rewritten files first, then the files are written, the rows are moved (a `Step` with its own undo), the services reload, the rows are moved a second time for anything filed under the old name meanwhile, and the files are committed as `renamed client group younger to kids`. A failure in any step puts back the files and the rows, and a failure in the second move reloads the services again.

References are found by walking each file's YAML nodes and replacing only the matching scalars. A name in quotes stays quoted. Names are matched in the sections the loader reads them from: rule conditions, `entry`, a quota's `ruleset`, an `evaluate` action's `ruleset` and inline `rules`, and the `group` or `groups` of a task. The check that runs before anything is written means a reference this walk missed would be refused by the loader, not saved broken.

Names are compared without regard to case, so a rename may change only case. A name is refused when stored rows are under it from an item no longer in the policy, which also covers `parent_checks` and `task_turns`. A usage preset that still names such an item is not counted as history. The MCP tools are unchanged.

### Acceptance test cases for S007.6

1. **Renaming** (Renaming, Time windows). Use a policy where a client group `younger` is named by a rule, a task in `tasks.d`, and a task in another file. Rename it to `kids` on Client Groups, then check each file, that comments and layout are the same, and `git log` in `config` for one commit `renamed client group younger to kids`. Repeat on a site group, a time window, a quota, and a rule set that `entry` names, and check the web and the quizzes decide as before.
2. **Refusals** (Renaming). Try a name in use, `default` for a client and a site group, a name with a colon, and a name differing only in case from another item. Leave history under a deleted group, then try its name. Check the dialog stays open with each reason, and a change of case alone is allowed.
3. **Unsaved changes** (Renaming). Change a field on any page, and check Rename is disabled with a title saying why, on the item pages and beside Save on a rule set's page.
4. **History** (History). After renaming a client group, check Minutes and Bytes, Attempts, a task's trend, the facts page, and spelling word statistics show the earlier days under the new name, and Today's score and tasks required are unchanged.
5. **Quota** (History). With 40 of 45 minutes of `entertainment` used, rename it to `fun` and check the sites close after 5 more minutes, and the graph shows earlier days under `fun`.
6. **Site group, transfer, preset** (History). Check the usage graph, the host drill-down, and the request table under a renamed site group. Rename while a large download runs, and check it is not cut. Save a preset that names a group and a quota, rename them, and open the preset.
7. **Failure** (Renaming). Make the database read-only, or stop the observations service, rename, and check every file and row is as before, with the reason in the status bar.
