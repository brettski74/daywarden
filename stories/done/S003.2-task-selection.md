# User Voice

As a child, I want YouTube to send me to a revision task I am allowed to do today, and I want a way to put that task down and try a different one if I am stuck. As a parent, I want "try a different one" not to count as finishing revision, and I want a task that is due, or that he has already put off enough times, to be the one he has to face.

# Use Cases

- The decision API, when it chooses `revision_task`, returns a `302` to a concrete URL on the task site for this client group.
- The picker looks only at tasks S003.1 says are eligible. `parent_check` is never eligible for the picker.
- When one or more of those tasks are required, the picker chooses only from the required ones. Otherwise it chooses from every eligible task.
- Inside that set, it chooses the task whose last pass is oldest. A task that has never been passed comes before any task that has. Ties are stable and not dependent on request order in a way that starves one task: equal candidates rotate.
- An in-progress attempt on the chosen task is resumed. A new attempt is not opened beside it.
- If no task is eligible, the page says so in plain language and does not redirect in a loop.
- A request for an optional task, including a direct URL for that task, is answered with a required task while any required task is eligible. The optional task is not started.
- Every child-facing task page has a control to try a different task. Using it on a task that is not required marks the current attempt abandoned and opens the next eligible task, excluding the one just abandoned in this visit so he does not immediately land on the same task.
- He may abandon a required task only when another required task is eligible. The attempt is marked abandoned, which marks that household day as one skip under S003.1, and the next page is another required task. That next task is one other than the task he just abandoned, when such a task exists. If every other required task was already abandoned earlier in this visit, he is sent back to a required task rather than to an optional one.
- When the task he is on is the only required task, the give-up control does not abandon it. The attempt stays `in_progress`, and the page tells him this task has to be finished before another one. Any other control that would abandon the attempt, including spelling practice in S005.3, follows the same rule.
- A failure starts the failure cooldown, marks that household day as one skip under S003.1, and does not increment the pass count. Another failure or abandon the same day does not add a skip. Until the task is eligible again, the picker may offer other eligible tasks. A skip recorded today does not make the task required today. A pass on a required task scores one point for the household day, the same as any other pass, and S003.1 then clears that task's skip days. The due date no longer makes it required, because a pass now exists.
- If no task is eligible, or a misconfigured required task cannot be finished, the household fixes the task or the assignment. The picker does not substitute an automatic pass.
- A built-in task type, `parent_check`, is never shown to the child. An authenticated parent records a pass of that task for a client group, as credit for work the server did not see. That pass adds one to the group's count for the household day. The child has no request that can record it. `available_from`, `due_date`, `max_skips`, and `max_passes` do nothing for this type. This task exists so the gate can be tried before S004, and so a parent can credit work done off the server afterwards.

# Acceptance Criteria

- [x] With two eligible tasks, neither required, one never passed and one passed last week, the picker returns the never-passed task.
- [x] With a required task that has never been passed, and an optional task that has also never been passed, the picker returns the required task.
- [x] A request that the rules redirect at 16:00 receives a `302` whose `Location` is a URL on the task site for that chosen task.
- [x] A URL for an optional task, requested while a required task is eligible, does not start the optional task. The response takes him to a required task.
- [x] Recording a `parent_check` pass as a parent increases today's pass count for that client group by one, and a second decision for YouTube then follows the rules with that new count. Once the count meets `tasks_required`, that decision does not redirect to revision solely because the count was short.
- [x] The picker never returns a `parent_check` task. The child has no request he can send that records a `parent_check` pass.
- [x] `available_from`, `due_date`, `max_skips`, and `max_passes` on a `parent_check` task still leave it out of the picker.
- [x] A task with `max_passes` of 3 and three stored passes for this client group is not offered, including after its pass cooldown has elapsed. Another eligible task is offered instead.
- [x] Choosing "try a different task" on a task that is not required marks the attempt abandoned, does not increase the pass count, and opens a different eligible task when one exists.
- [x] When that abandoned task was the only eligible one, the page says there is nothing else available right now.
- [x] Choosing "try a different task" on the only required task leaves the attempt `in_progress`, does not increase the pass count, and does not open another task.
- [x] With two required tasks, choosing "try a different task" marks the current attempt abandoned and opens the other required task. An optional task is not opened. Abandoning the second one still opens a required task.
- [x] On the three household days allowed by `max_skips` of 3, "try a different task" still abandons the task. On the next household day, with that task the only required one, "try a different task" does not abandon it.
- [x] A required task inside its failure cooldown is not offered. An optional eligible task is offered instead.
- [x] A task with `available_from` tomorrow is not the task offered today.
- [x] After the redirect, the task page loads. A policy rule that allows the task host is enough. The proxy bypass list is not required for this story.

# Notes

Depends on S003.1, S008.2, and S000.2. The child-facing pages in later quiz stories replace day-to-day use of `parent_check`. `parent_check` stays available as a parent-recorded credit. The follow-up request to the task host is a new decision. If the household policy does not allow that host, the quiz will not load. The sample in S008.5 has to allow it for the enrolled child, or the task host stays on the existing proxy bypass list. This story does not generate that list.

A required task is whatever S003.1 says is required for this client group today. This story does not invent a second definition. Most days the only eligible tasks are the ones with a short cooldown, and the picker has nothing required to enforce. The fields matter on the day a longer-cooldown task is eligible, due, or out of skips.

## Change Summary

The picker uses the eligibility and required rules from S003.1, and it never offers `parent_check`. When any eligible task is required, the choice stays inside that set. A task that has never been passed comes first. Otherwise the oldest pass comes first. Ties are ordered by name and then rotated, so one task is not stuck at the back of the list.

A rule that redirects to `revision_task` returns a `302` whose location is that task's page on the task site, `http://<task-host>/tasks/<name>`. The household URL is left as it is when nothing is eligible. Requesting that URL is allowed, and the page says there is nothing to revise, so it does not redirect again. A direct request for an optional task, or for `parent_check`, does not start that task while a required task is eligible. The response goes to a required task. A request that is already the task he may open is allowed, including when the rule said `revision_task`, so the page can load. A rule that allows the task host is enough. The proxy bypass list is not changed.

Opening a task resumes the in-progress attempt. "Try a different task" abandons it when the task is not required, and when it is required only if another required task is eligible. The next page skips tasks already abandoned in this visit. If that would leave no required task, he is sent back to a required one other than the one he just left, not to an optional task. The only required task stays `in_progress`, and the page says it has to be finished. `may_abandon` is the same answer spelling practice will use.

A failure still starts the failure cooldown and marks one skip for that household day. It does not add a pass, and a second failure or abandon that day does not add another skip. A pass on a required task scores one point and clears that task's skip days, so the due date no longer makes it required.

An authenticated parent records a `parent_check` pass from the attempts page. The row is an attempt, so today's count goes up by one and the next YouTube decision sees it. The child has no request that writes that pass. The four optional limits still do not put `parent_check` in the picker.

## Suggested Acceptance Testing

- With two eligible tasks, one never passed and one passed last week, confirm the redirect location is the never-passed task. Define them in either order and confirm two never-passed tasks alternate.
- Set a due date on one task and leave another optional. At 16:00, confirm YouTube is a `302` to the due task on the task-site host. Confirm a direct request for the optional task does not open an attempt and sends him to the due task.
- Allow the task host with a site-group rule. Confirm the task URL is allowed and the page shows "Try a different task". Confirm the host is not required on the bypass list.
- With nothing eligible, confirm YouTube redirects to the household `revision_task` URL, the next decision allows that URL, and the page says there is nothing to revise.
- Sign in as a parent and record a parent check for the younger group. Confirm today's pass count is one higher and YouTube is no longer redirected only because the count was short. Confirm a task-page post does not record a `parent_check` pass.
- Put `available_from`, `due_date`, `max_skips`, and `max_passes` on a `parent_check` task and confirm the picker still does not offer it.
- Store three passes on a task whose `max_passes` is 3, wait out the pass cooldown, and confirm a different eligible task is offered. Set `available_from` to tomorrow and confirm that task is not offered today. Fail a due task inside its failure cooldown and confirm an optional task is offered instead.
- On an optional task, choose "Try a different task" and confirm the attempt is abandoned, the pass count is unchanged, and another eligible task opens. When it was the only eligible task, confirm the page says there is nothing else available right now.
- On the only required task, choose "Try a different task" and confirm the same attempt stays `in_progress` and no other task opens. With two required tasks, confirm the first give-up opens the other required task, and giving up that one still opens a required task rather than an optional one.
- With `max_skips` of 3, abandon the only task on three household days and confirm each one is abandoned. On the next household day, confirm "Try a different task" does not abandon it.
- Come back to a task that is already in progress and confirm it is the same attempt. Pass it and confirm today's count goes up by one and the due date no longer makes it required.
