# User Voice

As a parent, I want to open a line on the usage graph and see which hosts it was spent on, in minutes and in bytes
each way, so that I can tell whether the entertainment time last week was YouTube, a game, or something I have not met
yet.

# Behaviour

## Host bar chart

- [ ] Double-clicking a line on the S030.1 graph, or pressing Enter on its legend entry, opens a bar chart beneath the
  graph with the shared expand animation. Its heading names the line and the range, such as
  `younger, Past week: top hosts`.
- [ ] The bar chart lists hosts down the left with a bar to the right for each, and the value at the end of the bar. It
  shows at most 20 hosts, the highest first. It covers the line's group within the same filters and range as the
  graph, in the page's unit.
- [ ] A host is the host name from the address fetched, with the port only when the address named a port other than the
  scheme's default, such as `www.youtube.com` or `localhost:3000`. Browsers drop `:443` from an `https` address and
  `:80` from an `http` one, so those are never shown.
- [ ] On the Minutes page, a host gains a bucket's length once for each bucket in which it sent or received any bytes,
  however many requests it served in that bucket. For example, a page whose HTML, three stylesheets, four scripts, and
  two images all come from `www.example.com` within one three-minute bucket gives `www.example.com` three minutes, not
  thirty. Another host used in the same bucket also gains those three minutes, so the bars can add up to more than the
  line. A line that covers several groups or quotas adds them, as in S030.1.
- [ ] On the Bytes page, each bar is split into downloaded and uploaded, told apart by colour and named in a key, with
  both figures at its end, such as `1.2 GB down, 40 MB up`. Hosts are ordered by the two added together.
- [ ] Double-clicking another line replaces the bar chart. A close button collapses it with the shared animation.
- [ ] The line drilled into is in the page address, so Reload, Back, and a bookmark open the bar chart too. Changing a
  filter or the range redraws both charts.
- [ ] *Added in implementation:* each legend entry is a button, so a click, Enter, or Space on it opens its line, and
  so does Enter on a line focused with Tab. Pointing at a line that can be opened shows the hand pointer.
- [ ] *Added in implementation:* the graph gives up half its height to the bar chart, which runs on below it as the
  content pane scrolls, and takes it back when the bar chart closes.
- [ ] *Added in implementation:* changing Group by, or choosing a preset, closes the bar chart, because the lines are
  then different ones. Saving or deleting a preset keeps it open, and following Minutes or Bytes in the sidebar keeps
  the line, so the same line's hosts show in the other unit. An address naming a line the graph cannot draw, such as
  `?client=older&by=client&range=past-week&line=younger`, shows no bar chart, and the status bar says
  `younger is not a line on this graph, so its hosts are not shown.`
- [ ] A range that starts before the oldest host detail kept says from when it is kept, such as
  `Hosts are kept for 30 days, from Wednesday 14 October 2026.`, and shows the hosts from then on. Before the upgrade,
  that date is the day of the upgrade.
- [ ] The S030.1 graph is unchanged by the upgrade and by the retention. Its totals still reach back to the install.

## Retention

- [ ] `host_retention` in the policy file sets how long host detail is kept, in whole days, such as
  `host_retention: 30d`. Left out, it is 30 days. A value that is not a whole number of days of at least one is a
  load error that names the key, and the policy in force stays.
- [ ] Host detail older than the retention is deleted at least once an hour, and when the service starts. The bar chart
  never shows anything older. Shortening the retention and running `dw reload` removes the older detail within the
  hour. *Changed in implementation:* a reload removes it at once, and `dw logs observations` says how many host rows
  went, such as `removed 1200 host rows older than 7 days`.
- [ ] *Added in implementation:* a retention written in hours, minutes, or seconds that comes to whole days is
  accepted, so `host_retention: 48h` is two days. `36h`, `0d`, and a bare `30` are load errors.

# Notes

## Design hints

- **Host buckets.** Two new tables beside the existing ones, such as `host_buckets` keyed by client group, site group,
  host, and bucket start, and `host_quota_buckets` keyed by client group, quota, host, and bucket start. Each holds the
  bucket's length, bytes down, and bytes up. `UsageStore.file_observation` writes them in the same transaction as the
  existing rows, with the same bucket placement and the same quotas. A second report for the same host in the same
  bucket adds bytes to the row and does not add time, which is what counts a page's ten requests once.
- **Why not match requests to buckets by time.** Counting the buckets that overlap any request to the host would also
  count buckets in which a connection was open but idle, such as a long poll or a paused video, and it needs an
  interval join over a month of requests on every drill-down. Recording the host when its bytes are filed counts a
  bucket only when that host moved bytes in it, which is how the site-group time is already counted, and the query is a
  plain sum.
- **The proxy.** Today one meter counts the request and response bodies of a flow together. It needs one meter per
  direction, and each report carries `bytes_up` and `bytes_down`, with `bytes` still the total the existing ledger
  files. The observations service takes the host from the URL it already receives. A report from an older proxy with
  only `bytes` is filed as downloaded.
- **Size.** At a 3m bucket and about 40 hosts a bucket, four hours a day is about 3,000 rows a day for each client
  group, under 100,000 in 30 days.
- The bar chart is a horizontal stacked bar chart in the S030.1 chart kit, using `d3-shape`'s stack.
- The retention lives in `policy/hierarchy.py` beside `bucket_length`. The observations service, which writes the
  rows, deletes the old ones.

## Out of scope

- Grouping hosts under one site. YouTube's video comes from many `*.googlevideo.com` hosts, such as
  `rr3---sn-ab5l6nrz.googlevideo.com`, which each get their own bar. The site group line already gives YouTube's total.
  A later story could group the bars by registrable domain.
- Upload and download apart on the S030.1 graph.

## Change Summary

The proxy keeps one meter per direction for each flow, sharing the report interval, so a report still goes out about
once a minute while bytes move and again when the flow ends, now with `bytes_up` and `bytes_down` as well as `bytes`.
The observations service checks that the two add up to the total, files the total as before, and files the same
report again under its host, beside the site group and beside each quota that accepted it, in the same transaction and
the same bucket. A second report for a host in a bucket adds its bytes and not its time.

There is no separate endpoint for the top hosts. The page's address names the line with `line=`, and the existing
`/parent/api/usage/minutes` and `/bytes` answer `hosts` beside the graph when it does. One request therefore redraws
both charts whenever a filter or the range changes, and the page loader, the address, and sign-in all work as for the
graph. A `line` is not a setting, so presets never hold one and preset matching ignores it.

The bar chart reads only host rows inside the range and from the kept-from day on: midnight `host_retention` days
before today, or the day of the earliest host bucket ever filed when that is later. That earliest bucket stands for the
day of the upgrade. It is the earliest rather than the first filed, so a proxy whose clock is behind cannot hide older
rows. The site-group and quota rows are never pruned, so the graph is unchanged. Pruning runs under the same lock that
guards each report, on a daemon thread every hour, at start, and after each successful reload.

The bar chart is SVG drawn by React on the same frame as the line chart. Host names and end values are measured with
`getComputedTextLength` after the first draw, which starts from a guess of their widths, so a long name such as a
`googlevideo.com` host never runs off the left edge.

## Suggested Acceptance Testing

### Acceptance test cases for S030.2

Rebuild and start with `make up`, so the proxy and the services run the new code. Sign in to the parent pages. The
child computers are in the younger and older client groups.

1. **Counting hosts on Minutes.** On the younger computer, browse a news site for a few minutes, then watch YouTube for
   ten. After the current bucket ends, open Minutes, Today, Group by Client group, and double-click the younger line.
   Compare the bars with the younger line's total, and look for `www.youtube.com` and the `googlevideo.com` hosts. Then
   double-click older, and press Enter on the younger legend entry and on the younger line after Tab. Covers the first
   four checks and the first two *Added in implementation* checks under Host bar chart.
2. **Bytes down and up.** On the younger computer, upload a large file to a site that takes uploads, such as a Google
   Drive or Classroom upload. Open Bytes, Today, and open younger. Check the key, the two colours, the end text, and
   that the upload site's bar is mostly uploaded. Covers the Bytes check.
3. **The address.** With younger open on Minutes, follow Bytes in the sidebar, reload, go Back, bookmark the address
   and open it in a new tab, then change Client groups and the Date range. Change Group by, then reopen a line and
   choose a preset, then reopen and save a preset. Open
   `/parent/usage/minutes?client=older&by=client&range=past-week&line=younger`. Close the bar chart with its button.
   Covers the address, replace, and close checks, and the third *Added in implementation* check.
4. **Host names with ports.** On a child computer, open a page served on a port that is not the default, such as a NAS
   admin page on `:5001` or a development server on `localhost:3000`, and an ordinary `https` site. Open that client
   group's line. Covers the host name check.
5. **Retention and the upgrade.** The day after the upgrade, open Past month and drill into a line, and check the note
   names the upgrade day while the graph still reaches back to the install. Set `host_retention: 1d` in the policy and
   run `dw reload`, then `dw logs observations`, and drill into Past week. Try `host_retention: 36h`, `0d`, and `30`
   with `dw check` and `dw reload`, then `48h`, and finally remove the line. With `host_retention: 1d` left in place
   overnight, run `dw restart` the next morning and look for the pruning line in `dw logs observations`. Covers Retention, the kept-from check, and the graph-unchanged check.
