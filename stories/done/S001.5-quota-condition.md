# User Voice

As a parent, I want a site group to close for the day once its time quota is used, even if revision is already finished.

# Use Cases

- A group may have a daily quota, stored as a duration in seconds, minutes, or hours. `2h` and `120m` are the same value. The configuration does not store a number of buckets.
- The condition `quota_remaining` is true when today's consumed time for this client and this group is strictly below that duration. Consumed time is the sum of the lengths of buckets that contained traffic and have already ended.
- Changing the bucket length does not change the stored duration.
- A group with no quota configured makes the condition true.
- Until S002.1 is filling buckets from real traffic, the consumed time is whatever the ledger store says, including a value written by a test.

# Acceptance Criteria

- [x] A quota written as `2h` is stored as two hours. The same value written as `120m` or `7200s` compares equal to it. A quota written as a bare bucket count is rejected.
- [x] With a `2h` quota and five-minute buckets, 23 ended buckets (115 minutes) leave the condition true, and 24 ended buckets (120 minutes) make it false.
- [x] Changing the bucket length from five minutes to ten minutes leaves that stored quota at two hours. Buckets already counted still contribute five minutes each. A new ended bucket contributes ten minutes.
- [x] A bucket whose end time is still in the future is not counted, even if it is marked active.
- [x] Yesterday's buckets are not counted today.
- [x] Another group's buckets are not counted against this group.
- [x] Another client's buckets are not counted against this client.
- [x] A group with no quota configured allows the condition to pass.
- [x] Plugged into the sample schedule from S001.3, at 16:00 on Wednesday with tasks already complete, remaining quota allows the request and exhausted quota denies it with the rule's message.

# Notes

Depends on S001.3. The real definition of a counted bucket is owned by S002.1. This story owns the condition and a small store that S002.1 will write to. Agree the store shape with S002.1 before implementing both.

## Change Summary

A group's `quota` is a duration with a unit. `2h`, `120m`, and `7200s` are stored as the same 7200 seconds on `site_groups.quota_seconds`. A bare number, including `24` and `7200`, is rejected, and so is text such as `24 buckets`. The design note that a unitless number means seconds is not what the file accepts: every accepted spelling carries `h`, `m`, or `s`, so a bucket count cannot sneak in as a raw integer. Leave `quota` off and the column stays NULL. `quota_remaining` is then true no matter how many buckets are stored. When a quota is set, the condition is true only while today's consumed seconds are strictly below it. 23 ended five-minute buckets are 115 minutes and still allowed. 24 are 120 minutes and the rule denies with its own message.

`household.bucket_length` is the length used when a new bucket is opened. It defaults to five minutes (`300` seconds) and is stored in `settings`, separate from every quota. Reloading the file with `10m` leaves `quota_seconds` at 7200 and does not resize rows already stored. Those still contribute 300 seconds each. A bucket opened after the change contributes 600.

The ledger is `usage_buckets`. A row is one bucket that contained traffic, keyed by client, site group, and household-local start. The offset on an aware start is dropped, not converted, so 00:30 in the household zone stays on that local date. The row stores the length it was opened with and a `byte_count` that later observations add to. A second observation does not insert a second row and does not change the length. `PolicyStore.consumed_seconds` sums lengths for this client and this group on the local date of the request, and only when the request time is at or after the bucket's end. An open bucket is stored and still not counted. Yesterday's rows are not counted today. Another client or another group is not counted. An IP that is not a client has used none.

There is a gap where those two rules meet. A bucket that starts today and ends after midnight has not ended while it is still today, and it is yesterday's bucket once the date rolls, so it is never counted. With five-minute buckets that is only a bucket opened in the last five minutes of the day.

The boolean `quota_remaining` argument on `evaluate` and `decide` is gone. Callers pass `consumed` seconds, and the group's quota comes from the group. The default is no usage. S002.1 writes the rows; the condition reads them, with no test double left in the decision path. The agreed columns and method names are recorded on S002.1.

The rows live in schema version 5. A version-4 database gains `quota_seconds` (NULL on existing groups) and the empty `usage_buckets` table, and keeps its groups. Reloading the policy file keeps the buckets, because the client and the group keep their ids. Removing either one drops the buckets that belonged to it. The service holds its database connection open and reads the ledger on every decision, so a bucket written by another connection is used on the next request without a restart.

## Suggested Acceptance Testing

- Run `python -m pytest tests/test_policy_quota.py tests/test_policy_rules.py tests/test_policy_decisions.py tests/test_policy_groups.py`. No Docker is needed. These cover `2h` / `120m` / `7200s`, rejection of a bare number, the 23-bucket and 24-bucket threshold, the five-minute to ten-minute length change, an open bucket at 15:59:59 and at 16:00, yesterday's buckets including a 00:30 household-local bucket that is still the previous UTC date, the other client, the other group, a group with no quota, the Wednesday 16:00 schedule with tasks already complete, a second observation in the same bucket, a reload that keeps the ledger, a second database connection, and a version-4 upgrade.
- Rebuild is part of the service test. Run `python -m pytest tests/test_policy_service.py`. It posts the Wednesday 16:00 request with the revision count already at 2, first after 23 five-minute buckets and then after 24. The image is what the container runs.
- On the real stack, put `quota = "2h"` on a group that has a `quota_remaining` rule, and `docker compose up -d --build decisions`. `docker compose logs decisions` should show `usage buckets are 5m` and `quota 2h` on that group. A group with no quota should show `no quota`. With an empty ledger, a request that reaches the rule is allowed.
- Leave the unit off. `quota = 24`, `quota = "24"`, and `quota = 7200` should all fail to load. The seconds spelling of the same two hours is `quota = "7200s"`. The decisions service should fail to start on the bare numbers, and the log should say the quota is a duration, not a number of buckets.
- Write buckets without restarting. Use household-local starts, not UTC. A count of 23 ended five-minute buckets, with today's revision count already satisfied, should allow the next request. A 24th should deny with the rule's message.

  ```sh
  docker compose exec -T decisions python - <<'PY'
  from datetime import datetime, timedelta
  from policy.store import PolicyStore
  store = PolicyStore("/var/lib/daywarden/policy.sqlite3")
  (client_id,) = store.connection.execute(
      "SELECT id FROM clients WHERE name = ?", ("Younger child",)
  ).fetchone()
  start = datetime.fromisoformat("2026-10-21T08:00:00")
  for index in range(24):
      store.mark_bucket(client_id, "Entertainment", start + timedelta(minutes=5) * index)
  store.close()
  PY
  ```

- Change `household.bucket_length` from `5m` to `10m` and restart. The log should show `usage buckets are 10m` and the same `quota 2h`. Buckets written before the restart should still be five minutes long in `usage_buckets.length_seconds`.
- Store 24 buckets for yesterday's household date and leave today empty. Today's request should still be allowed.
- Give the other client 24 buckets, or give them to another group, and leave this client and this group empty. This client's request should still be allowed.
- Remove `quota` from the group and restart. The same 24 buckets should no longer deny the request.
- An existing `policy-data` volume from schema 4 should migrate on restart. The log should show the stored policy loading, not a schema error.
