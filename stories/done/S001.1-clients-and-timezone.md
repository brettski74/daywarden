# User Voice

As a parent, I want the authorization service to know which child an IP address belongs to, and what "today" means in our house, so that limits do not drift with UTC.

# Use Cases

- Configure a household IANA timezone. If none is set, use the timezone of the machine running the service.
- Configure one or more clients. Each client has a source IP and a display name. The IP is the DHCP reservation for that computer.
- The household has two children. The first configuration enrols the younger child's reserved IP. The older child's reserved IP can be stored later as a second client, with separate tasks, revision counts, and usage.
- Site rules are the same for every client. Per-client differences in this version are task assignment, the revision count, and the usage ledger.
- A decision for an IP that has no client record still runs the household rules. The client record is there for names, task assignment, and reports. It is not an allow-list of who may use the proxy. An unenrolled IP that is asked to do revision will find no assigned task.

# Acceptance Criteria

- [x] The timezone and the clients are stored in SQLite and survive a restart.
- [x] "Today" and the current local time used by later rules come from that timezone, not from the UTC date alone.
- [x] A decision request includes the client IP. The service resolves the display name when one exists and still returns a decision when it does not.
- [x] Two clients can be stored at once. The sample data enrols the younger child only, and a second client can be added without changing the schema.
- [x] Unit tests cover a date just before and just after local midnight, including a timezone that is not UTC.

# Notes

Depends on nothing in S000 except the decision request shape. Can be built beside the addon. Different hours for each child are not part of this story.
Clients should be able to be configured by IP address or DNS name. It is expected that configuration will most often use DNS names rather than IP addresses and the system should resolve them into IP addresses as efficiently as possible - probably by doing the resolution during the initial config load rather than on processing every request.

## Change Summary

The policy service is a FastAPI app in `policy/`, built from its own image. It replaces the decision stub as the Compose service `decisions`, so the addon and `DECISION_URL` are unchanged. The image is rebuilt on every `docker compose up` (`pull_policy: build`), so a code change cannot leave a stale container running.

`config/policy.toml` holds `[household] timezone` and one `[[clients]]` table per computer. Each client has a `name` and an `address`, written as an IP or a DNS name. On start the file is validated and written into SQLite in one transaction. The database lives in the `policy-data` volume, and the schema has three tables: `settings`, `clients` and `client_ips`. DNS names are resolved at that point, never per request. A decision is a dictionary lookup by IP, and IPv4-mapped IPv6 addresses match their IPv4 client. If a name fails to resolve, the client keeps the IPs stored by the last load that did resolve it. If the file is absent, the stored policy is used as is. Two clients with the same IP are rejected, and nothing is stored. A client keeps its row id while its name stays the same, so later per-client records stay attached. The sample enrols only the younger child, with a placeholder IP, and has a commented-out older-child entry.

`HouseholdClock` turns the request's `occurred_at` (or now) into household-local time and a local date. With no configured timezone it uses the host's zone. Compose mounts the host's `/etc/localtime` at `/etc/host-localtime` for this; `TZ` takes precedence when it is set.

Until S001.3 adds the rule engine, the "household rules" are still the single decision in `config/decision.json`, read on every request. Every request gets that decision, enrolled or not. A malformed request (for example, one with no valid `client_ip`) gets `400`, which the addon already treats as an unrecognized decision and turns into a `403`. The addon's decision shape is strict, so the decision response does not carry the client name. Instead, the name goes into the decision log, `/tmp/decisions.jsonl`. Each entry is now `{"request", "client", "local_time", "decision"}`, and the S000 tests that read it were updated. The integration tests' `down` now passes `-v` so each run removes its policy volume.

## Suggested Acceptance Testing

- Run `python -m pytest tests/test_policy_clock.py tests/test_policy_clients.py tests/test_policy_decisions.py`. These need no Docker and cover local midnight in Toronto, Sydney and UTC, plus a DST change.
- Run `python -m pytest tests/test_policy_service.py`. It configures Sydney time, one client by IP and one by DNS name, then recreates the container without the file and checks that both still resolve.
- Replace the placeholder in `config/policy.toml` with the younger child's real reservation (try the DNS name), run `make up`, and check `docker compose logs decisions`. It should show the timezone, the current local time, and the IP the name resolved to.
- Browse from the younger child's computer, then run `docker compose exec decisions tail -n 3 /tmp/decisions.jsonl`. Expect `"client": "Younger child"` and a `local_time` in household time, not UTC.
- Browse from a computer that is not listed and confirm it still gets the configured decision, with `"client": null` in the log.
- Set `timezone = "Australia/Sydney"` in `[household]`, restart `decisions`, and confirm `local_time` in new log entries jumps to Sydney time. Remove the line again and confirm it goes back to this machine's zone.
- Put a typo in the timezone and confirm `make up` fails loudly, with the error in `docker compose logs decisions`, rather than starting with the wrong clock.
- Known, and not from this story: `tests/test_run_proxy.py` uses the repo's own `config/`, and the committed `config/decision.json` is a deny. Two of its tests fail for that reason both on `HEAD` before this change and after it.
