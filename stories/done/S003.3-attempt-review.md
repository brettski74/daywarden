# User Voice

As a parent, I want to see which tasks he attempted, what he answered, and whether he passed, so that I can see what he has learned and where he is stuck.

# Use Cases

- A page lists attempts for a client group, newest first, with the task name, start time, outcome, and duration.
- Opening an attempt shows the stored answers and results in a readable form. Quiz stories add type-specific detail. This story must at least show the raw record cleanly for `parent_check` and for a generic answer list.
- The page is not available to the child. It is served over HTTPS with the parent session from S007.1. A missing session, an idle session, and a session past its lifetime all show the sign-in form and no attempts.
- From this page, a parent records a `parent_check` pass for a client group without the child opening a task. That is the credit described in S003.2.

# Acceptance Criteria

- [x] A pass, a failure, and an abandonment each appear with the correct outcome and household-local times.
- [x] An attempt with a list of answers shows each answer, not only the final outcome.
- [x] The page is protected by the parent session from S007.1. With no valid session it shows the sign-in form and no attempts, including when the idle limit or the lifetime has run out.
- [x] The parent records a `parent_check` pass for a chosen client group from this page, without the child opening a task. That action is the only way that task type reaches a pass. The new row appears in the list as a pass.

# Notes

Depends on S003.1, S003.2, and S007.1. The client on the page is the client group the attempt was recorded for. Later quiz stories extend the detail view rather than building a second history. The temporary usage-report password from S002.2 is not a session for this page.

## Change Summary

A signed-in parent chooses a client group and sees that group's attempts, newest first. Each row shows the task, the household-local start and finish, the outcome, and the duration. An attempt still in progress says it is still going. Opening a row shows the stored record. A list of answers is shown one answer at a time, including an answer that is itself a set of fields. A `parent_check` row shows the fields that were stored with it, including who recorded it.

The page stays behind the parent session. No account leaves it closed. A missing session, a session past the idle limit, and a session past its lifetime all show the sign-in form and none of the attempts. Plain HTTP does not return the page. Recording a parent check posts to `/attempts/parent-check` for a client group in the household. That writes a pass attempt for the group's `parent_check` task, so today's count goes up and the new row is in the list. The child still has no request that writes that pass.

## Suggested Acceptance Testing

### Acceptance test cases

1. Sign in and open `/attempts` for a client group that has a pass, a failure, and an abandonment. Confirm each row shows that outcome, the household-local start and finish, and the duration, with the newest start first. Confirm another group's attempts are not in the list.
2. Open the pass. Confirm each stored answer is listed. Open a failure whose answers are fields and confirm each field is shown, along with the outcome.
3. With no cookie, with a session idle for 15 minutes and one second, and with a session 180 minutes and one second from sign-in, confirm `/attempts` and an attempt URL show the sign-in form and no task names or answers. Confirm the same with no parent account: the page stays closed and shows no attempts.
4. From `/attempts`, record a parent check for the younger group without opening a task as the child. Confirm the new row is a pass for that group's `parent_check` task, today's pass count is one higher, and a task-page request still cannot record that pass.
5. Open the parent-check row and confirm the stored record is readable. Request `/attempts` over plain HTTP and confirm the body is the HTTPS refusal and includes no attempts.
