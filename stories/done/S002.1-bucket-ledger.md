# User Voice

As a parent, I want a two-hour YouTube limit to stay two hours even if we later change how finely we measure it, and I want one stray request at the start of a bucket not to wipe out the rest of that bucket. I want the day's buckets to meet midnight.

# Use Cases

- The bucket length is configurable. The default is five minutes. It is not part of the quota. The length in seconds divides 86400 with nothing left over, so a grid that starts at local midnight also ends at the next midnight.
- A group's quota is the duration from S001.5. This ledger reports consumed time by adding up ended buckets. It does not store the quota as a bucket count, and it does not divide the duration by the bucket length and save the result.
- An observation is matched to a site group the same way a decision is. Traffic that matches no group, and no default group, is ignored.
- The observation marks the bucket that contains its timestamp, for that client and group, and adds its byte count to that bucket. On an ordinary day that bucket starts at a midnight boundary of the length in force and stores that length.
- A marked bucket contributes its stored length to the consumed time only when the current time is at or past the bucket's end.
- A new length applies only when the policy is loaded, which a restart does and which a reload of the policy file does. Until that load, observations stay on the previous midnight grid. The load ends each bucket that has not yet ended. That bucket's final length is the time from its start to the load, and that is what it contributes. The next bucket starts at the load and ends at the next midnight boundary of the new length, so it can be shorter than the configured length. Every bucket after that boundary is the full new length. A load that leaves the length unchanged does not close anything.

# Acceptance Criteria

- [x] An observation at 15:00:01 marks the bucket that started at 15:00:00. At 15:04:00 that bucket is not yet counted. At 15:05:00 it is counted.
- [x] A second observation in the same bucket does not create a second counted bucket. Its bytes are added.
- [x] An observation at 15:06:00 marks the next bucket.
- [x] Twenty-four ended five-minute buckets on the same local day, for the same client and group, add up to two hours. Twenty-three add up to 115 minutes.
- [x] Buckets from the previous local day do not count.
- [x] The bucket length divides 86400 seconds. Two minutes, five minutes, and ten minutes are accepted. Seven minutes is rejected.
- [x] Buckets are aligned to household-local midnight. With a five-minute length, an observation at 15:02:00 marks the bucket that started at 15:00:00. An observation at 23:58:00 marks the bucket that started at 23:55:00 and ends at the next midnight.
- [x] Changing the bucket length does not rewrite the configured quota. A bucket that has already ended keeps the length it stored.
- [x] The new length takes effect at the load that stores it. With five-minute buckets, a load at 15:02:30 that sets the length to two minutes ends the bucket that began at 15:00:00. That bucket's final length is 2 minutes 30 seconds, and that is what it contributes. The next bucket starts at 15:02:30 and ends at 15:04:00, so a marked one contributes 90 seconds. An observation at 15:03:00 marks that bucket and does not open another. Each bucket after 15:04:00 is two minutes long: 15:04:00, 15:06:00, 15:08:00, and so on.
- [x] The observation endpoint answers success without blocking the proxy when the URL matches a group, and it does not return an error to the proxy when the URL matches nothing.
- [x] The quota condition from S001.5 reads this ledger rather than a test double.

# Notes

Depends on S000.3, S001.2, and S001.5. Idle connections produce no observations, which is guaranteed by S000.3, so an open socket alone does not mark a bucket.

The ledger this story writes is the one S001.5 reads. `usage_buckets` is keyed by client, site group, and the household-local start (`started_at`, to the second, offset dropped rather than converted). `day` is that start's local date. `length_seconds` is that bucket's length, and the end is the start plus that length. On the grid it is the configured length. The load that changes the length rewrites it on a bucket that is still open, down to the seconds from its start to the load, and does not rewrite a bucket that has already ended. The first bucket of the new length stores the seconds from the load to the next midnight boundary. A second observation in the same bucket updates `byte_count` and does not change the length or insert a row. `site_groups.quota_seconds` is the group's duration from `quota`, or NULL when the group has none. It is not a bucket count. `settings.bucket_length` is the current length in seconds and defaults to 300. `PolicyStore.mark_bucket(client_id, group_name, started_at, length_seconds=None, byte_count=0)` opens or updates a row. `PolicyStore.consumed_seconds(client_id, group_name, at)` is what `quota_remaining` reads: the sum of `length_seconds` for that client and group on the local date of `at`, counting a bucket only when `at` is at or past its end. This story still owns alignment, the observation endpoint, and filling those rows from traffic. A row exists only when the bucket contained traffic, so there is no separate active flag.

Midnight alignment is a grid of the configured length counted from household-local midnight. The start that contains an observation is midnight plus the whole number of lengths that fit into the time since midnight. The length has to divide 86400 so the last boundary of an ordinary day is the next midnight. S001.5 accepted any length of at least one second; this story rejects a length that does not divide 86400, including seven minutes. A daylight-saving day is not 86400 seconds, and this story does not add a special case for it. The bucket that ends exactly on midnight is still the gap S001.5 describes: it has not ended during its own day, and the next day does not count it.

A change to the length is applied only by a load of the policy. Today that load is a process start. The same close applies if a later change loads the file without exiting. There are two ways to keep the grid on midnight across that change. This story uses the first.

The load that stores a different length finds every bucket whose end is still in the future and sets its length to the seconds from its start to the load. In the acceptance example the 15:00:00 bucket becomes 150 seconds and counts from 15:02:30. The next alignment point is the first midnight boundary of the new length that is strictly after the load. The bucket that covers the load up to that boundary starts at the load time, not at the first observation, and its length is the seconds between the two. Two-minute buckets make that 15:02:30–15:04:00, which is 90 seconds. An observation at 15:03:00 marks that bucket. From the boundary on, each bucket starts on the grid and lasts the configured length: 15:04:00, 15:06:00, 15:08:00. A load that already falls on a boundary has no short bucket; the next one is a full length. A load that stores the same length does not shorten a bucket, and the next observation rejoins the cell it already belongs to. The shortened 150 seconds and the following 90 seconds meet at 15:02:30 and add up to the four minutes from 15:00:00 to 15:04:00.

The other way is to keep today's grid and apply the new length at the next local midnight. Nothing is closed early, no short bucket is opened, and the rest of today is unchanged. This story does not do that. The length in the file takes effect at the load, and the short bucket is what puts the rest of the day back on a midnight grid.

## Change Summary

An observation is matched to a client and a site group the same way a decision is. The bucket it marks is the one that contains its household-local time. With a five-minute length, 15:00:01 and 15:02:00 both mark 15:00:00, and 23:58:00 marks 23:55:00, which ends at the next midnight. A second report in that bucket adds bytes and does not insert another row or change the length. The bucket counts only once the clock is at or past its end, so 15:04:00 is still inside a five-minute bucket that started at 15:00:00, and 15:05:00 counts it. Twenty-three ended buckets are 115 minutes. Twenty-four are two hours, and `quota_remaining` denies from that total. Yesterday's buckets, another client's buckets, and a URL in no group are left out. A group with no quota, and the default group, are still marked.

`household.bucket_length` has to divide 86400 seconds. `2m`, `5m`, and `10m` load. `7m` does not. The default stays five minutes. The quota stays a duration on the group. Changing the length does not rewrite it.

The grid changes only when a load stores a different length. A restart does that, and so does any later load of the file. The first load only establishes the midnight grid, including when the file's length is not the five-minute default. A later load of the same length leaves open buckets alone. A later load of a new length shortens every bucket that has started and has not yet ended, down to the seconds from its start to the load, for every client and group. A bucket that has already ended keeps the length it stored. The history of lengths is `settings.bucket_regimes`. Until the next midnight boundary of the new length, a report marks one bucket that starts at the load. In the acceptance example that is 15:02:30 to 15:04:00, 90 seconds. From 15:04:00 on, the buckets are the full new length: 15:04:00, 15:06:00, 15:08:00. A load that already falls on a boundary has no short bucket. A report timestamped before the load still uses the previous grid, and if that bucket was open at the load its stored length is the shortened one.

`POST /v1/observations` is the observations service, `python -m policy.observations`, on the policy image, sharing the policy database. It answers 204 when the URL is in a group and the bucket is marked. It also answers 204 when the URL matches nothing, the client is not enrolled, or the byte count is zero, and it writes no row. A malformed body is 400. The proxy still treats a failure or a stopped service as a log line, not as a change to the allow, deny, or redirect. The service keeps the jsonl log the addon tests read. `quota_remaining` reads `consumed_seconds` on the rows this service writes. A bucket written by the observations container is visible to the decisions container on the next request.

- Run `python -m pytest tests/test_policy_buckets.py tests/test_policy_quota.py`. No Docker is needed. These cover the 15:00:01 bucket, the open bucket at 15:04:00 and the counted bucket at 15:05:00, a second report adding bytes, the 15:06:00 bucket, 23 and 24 buckets against a `2h` quota, yesterday, another client, `2m` / `5m` / `10m`, rejection of `7m`, midnight alignment including 23:58:00, a UTC timestamp converted into the household zone, the 15:02:30 change to two minutes (150 seconds, then 90, then 15:04:00 / 15:06:00 / 15:08:00) for both children, an ended bucket that stays five minutes, a load on a boundary, a same-length reload, the first load of `2m`, a report timestamped before the load, a length change with no load time, a group with no quota, the default group, an unknown client, and the HTTP 204 / 400 answers.
- Run `python -m pytest tests/test_policy_service.py tests/test_report_observations.py`. The service test posts a YouTube report and an ungrouped report at the observations container, then reads the ledger from the decisions container: one row, 140 bytes, uncounted at 15:04:00 and five minutes at 15:05:00. The report test is the proxy. A stopped observations container still leaves an allowed page allowed.
- On the real stack, `docker compose up -d --build`. `docker compose logs decisions` should show `usage buckets are 5m`. Play a short YouTube video from an enrolled computer and confirm `docker compose logs observations` shows the URL and a byte count. The matching `usage_buckets` row has `length_seconds` 300 and a `started_at` on a five-minute midnight boundary. A second minute of the same video adds bytes to that row. Before the boundary, a request that reaches `quota_remaining` still sees the previous total. After the boundary, it sees another five minutes.
- Set `household.bucket_length` to `7m` and restart decisions. The service should fail to load, and the log should say the length has to divide the day so the buckets meet midnight. `2m`, `5m`, and `10m` should load. The group's `quota` stays whatever it was.
- With five-minute buckets and an open YouTube bucket, set the length to `2m` and `docker compose restart decisions` during that bucket. The open row's `length_seconds` should be the seconds from its start to the restart. The next report should mark one bucket that starts at the restart and ends at the next two-minute midnight boundary. Reports after that boundary should be two minutes apart. A bucket that had already ended should still show 300.
- Restart decisions without changing the length. The open bucket's `length_seconds` should stay 300, and the next report should join that same bucket.
- Request a host that is in no group, with no default group configured. The observations log should show the report, the proxy should still return the page, and `usage_buckets` should gain no row. A default group should gain a row. Classroom, which has no quota, should gain a row too.
