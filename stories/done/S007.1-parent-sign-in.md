# User Voice

As a parent, I want the reports and the editors behind a sign-in, so that he cannot mark his own revision finished or raise his own YouTube quota.

# Use Cases

- Parent accounts live in a local table on the decisions service: a username and a password hash. There is no sign-up page and no account for the child.
- A host command adds or replaces one username. It reads the password once, stores only the hash, and does not write the password into the policy file. Replacing a password ends that account's sessions.
- The hash is Argon2id. The stored string includes the salt and the parameters. The salt is new for each password. The parameters are at least the OWASP minimum for Argon2id: 19 MiB of memory, 2 iterations, and parallelism 1. Verification uses the parameters in the stored string.
- With no accounts, a parent page stays closed and shows no protected data.
- With at least one account, a parent page with no valid session shows a username and password form and no protected data.
- The right username and password start a session. The session key is 256 bits from the operating system's cryptographic random source. The browser receives the key in a `Secure` and `HttpOnly` cookie. The service stores a SHA-256 hash of the key, the account, the time of sign-in, and the time of the last accepted request. It does not store the key itself. Argon2 is for the password. The session key is already random, so a fast hash is enough.
- Parent pages are served only over HTTPS. The certificate is signed by the household CA from S000.1, the same CA the browsers already trust for the proxy. A browser that does not trust that CA gets a warning, not a plain HTTP copy of the page. Plain HTTP does not return parent pages, does not set the session cookie, and does not accept an authenticated action.
- The certificate names are configuration: the DNS names and IP addresses the parent uses to open the service. They are not taken from the `Host` header of a request. An empty name list is a startup error for this listener. The service does not sign a certificate for whatever name a visitor asks for.
- A new certificate is valid for 30 days. The service issues one when it has none, when the current one does not cover the configured names, or when the current one expires within 3 days. Otherwise it keeps the certificate it already has, including across a restart. The private key stays beside the CA material and is not written into the policy file or the repository.
- A missing username and a wrong password both refuse, show the same failure, and do not start a session. The missing-username case still runs a password hash check, so the two refusals are not told apart by how long they take.
- A session stays valid while both of these are true. The time since sign-in is at most the lifetime, which defaults to 180 minutes. The time since the last accepted authenticated request is at most the idle limit, which defaults to 15 minutes. Either limit may be set in the service configuration. A value that is missing uses the default. A value that is not a positive duration is a startup error.
- An accepted authenticated request updates the idle time. It does not move the sign-in time. A request that fails either limit does not update the idle time, does not return protected data, and is not acted on. The parent sees the sign-in form. The old key cannot be used again.
- Signing in again creates a new key. Older keys for that account stay valid until their own limits run out.
- Quiz pages, the decision API, and the observation API do not use this session.
- The usage report and the attempt review use this sign-in. The temporary `PARENT_PASSWORD` gate from S002.2 is retired here. A cookie from that gate is not a session.

# Acceptance Criteria

- [x] With no parent accounts, the usage report and the attempt review stay closed and show no usage and no attempts.
- [x] With an account and no session, those pages ask for a username and password and show no protected data.
- [x] The right username and password set the cookie. The next parent page opens without asking again.
- [x] A wrong password, and an unknown username, both leave the visitor on the form with the same failure and no cookie.
- [x] The password in SQLite is an Argon2id hash. The plaintext password is not in the database, the policy file, or the session row. The session row holds the SHA-256 of the key, not the key.
- [x] A request 15 minutes after the last accepted request, to the second, is still accepted when the lifetime has not run out. A request one second later is the sign-in form, and it does not refresh the idle time.
- [x] A request every few minutes is still accepted at 180 minutes from sign-in, to the second. A request one second later is the sign-in form, even though the idle limit was never reached.
- [x] With the idle limit configured as 1 minute and the lifetime as 5 minutes, those shorter limits are the ones that expire the session.
- [x] A `parent_check` post with an expired or missing session does not record a pass.
- [x] The decision API and the observation API still work with no parent session, from the proxy only. They are not a way to edit policy or record a pass.
- [x] A quiz page loads with no parent session.
- [x] A password in the query string does not start a session. A cookie from the old `PARENT_PASSWORD` gate does not either.
- [x] A parent page request over HTTPS presents a certificate signed by the household CA, covering the configured names, and valid for 30 days from issue.
- [x] With more than 3 days of validity left and the same configured names, a restart presents the same certificate. It does not issue another.
- [x] With 3 days or less of validity left, or with a configured name missing from the certificate, the next start issues a new certificate valid for 30 days.
- [x] The session cookie is `Secure` and `HttpOnly`. A request that is not HTTPS does not receive parent page contents and does not set that cookie.

# Notes

Depends on S002.2 and S003.3 existing, or lands first with a placeholder page and those stories adopt it. Prefer landing this story before either report is left running on the household network without it. S003.3 and S008.4 both use this session. S007.2 and S007.3 use it when those editors exist.

The proxy port itself stays an HTTP proxy. Browsers use that to open a tunnel. It is not a page, and this story does not wrap it in TLS. Calls from the proxy to the decision and observation APIs stay on the compose network and do not carry this cookie. The task site this project serves uses the same certificate rules when it exists. The placeholder `revision_task` URL stays until that site is there.

A parent browser accepts the certificate when it trusts the household CA. The child-computer note already installs that CA. A parent machine that is not one of those computers needs the same PEM.

## Change Summary

Parent accounts live in the decisions SQLite database. A username is added or replaced with `python -m policy.accounts USERNAME`, which reads the password once and stores an Argon2id hash (19 MiB, 2 iterations, parallelism 1). Replacing a password deletes that account's sessions. The usage report and the placeholder attempt review stay closed until an account exists. A valid session is a 256-bit key in a `Secure` and `HttpOnly` cookie. The database stores the SHA-256 of that key. A session lasts at most 180 minutes from sign-in and 15 minutes from the last accepted request, inclusive to the second. Either limit can be set with `PARENT_IDLE` and `PARENT_LIFETIME`. A request past either limit shows the sign-in form, writes nothing, and the old key cannot be used again.

Parent pages are served only on the HTTPS listener. The certificate is signed by the mitmproxy household CA, covers `PARENT_NAMES`, and is valid for 30 days. A restart keeps it while more than 3 days remain and every configured name is still on it. Plain HTTP, including a request that sends `X-Forwarded-Proto: https`, returns a short refusal and does not set the cookie. The decision API, the observation API, and `GET /quiz` do not use this session.

`/attempts` is a placeholder so the gate exists before S003.3. A `parent_check` is recorded only after a valid session is accepted. S003.3 can replace that table.

## Suggested Acceptance Testing

- Run `python -m pytest tests/test_parent_signin.py tests/test_parent_certificate.py tests/test_policy_report.py tests/test_usage_report.py tests/test_policy_volume.py tests/test_policy_service.py`. The service test builds the decisions image and needs Docker.
- With the stack up and no account, open `https://127.0.0.1:8090/usage` and `https://127.0.0.1:8090/attempts`. Both stay closed and show no usage and no attempts. Trust `data/ca/mitmproxy-ca-cert.pem` first, or expect the browser warning.
- Run `docker compose exec decisions python -m policy.accounts ada`, type a password once, and confirm `config/policy.yaml` is unchanged. Sign in on the usage page. Reload it and confirm it opens without asking again. Open `/attempts` in the same browser and confirm that page opens too.
- Sign out of the browser, then try an unknown username and a wrong password. Both show "That username or password is not right." and neither sets a cookie.
- In the database, confirm the password column starts with `$argon2id$` and contains `m=19456,t=2,p=1`, and that a session row stores a SHA-256 hex digest rather than the cookie value.
- Wait 15 minutes from the last accepted request and reload. That request still opens the page. One second later the form is back, and the old cookie does not open it again. Separately, keep using the page and confirm it still opens at 180 minutes from sign-in and shows the form one second later.
- Set `PARENT_IDLE=1m` and `PARENT_LIFETIME=5m`, recreate decisions, and confirm those shorter limits are the ones that expire the session. Set `PARENT_IDLE=nope` and confirm decisions refuses to start.
- Post a parent check with no cookie, and again with an expired cookie. Confirm no new pass is stored. Post one with a valid session and confirm it is listed.
- From the proxy, request a decision and send an observation with no parent cookie. Both still succeed. Neither edits the policy file nor records a pass. `GET /quiz` loads with no cookie.
- Put the password in the query string and confirm the page stays on the form. Send the old `PARENT_PASSWORD` cookie and confirm it is not a session.
- Inspect the certificate on `https://127.0.0.1:8090/usage`. It is signed by the household CA, includes every name in `PARENT_NAMES`, and expires 30 days after it was issued. Restart decisions while more than 3 days remain and confirm the certificate bytes are unchanged. Set the expiry inside 3 days, or add a name to `PARENT_NAMES`, and confirm the next start issues a new 30-day certificate.
- From inside the decisions container, request `http://127.0.0.1:8090/usage`, including with `X-Forwarded-Proto: https`. The body is the HTTPS refusal, and there is no `Set-Cookie`. The published host port is the HTTPS listener, so a plain HTTP client on that port does not get the page either.
- Confirm `data/ca/parent-key.pem` is mode 600 and is not in the git repository.
