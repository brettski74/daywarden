# User Voice

As a parent, I want the authorization service to know which child an IP address belongs to, and what "today" means in our house, so that limits do not drift with UTC.

# Use Cases

- Configure a household IANA timezone. If none is set, use the timezone of the machine running the service.
- Configure one or more clients. Each client has a source IP and a display name. The IP is the DHCP reservation for that computer.
- The household has two children. The first configuration enrols the younger child's reserved IP. The older child's reserved IP can be stored later as a second client, with separate tasks, revision counts, and usage.
- Site rules are the same for every client. Per-client differences in this version are task assignment, the revision count, and the usage ledger.
- A decision for an IP that has no client record still runs the household rules. The client record is there for names, task assignment, and reports. It is not an allow-list of who may use the proxy. An unenrolled IP that is asked to do revision will find no assigned task.

# Acceptance Criteria

- [ ] The timezone and the clients are stored in SQLite and survive a restart.
- [ ] "Today" and the current local time used by later rules come from that timezone, not from the UTC date alone.
- [ ] A decision request includes the client IP. The service resolves the display name when one exists and still returns a decision when it does not.
- [ ] Two clients can be stored at once. The sample data enrols the younger child only, and a second client can be added without changing the schema.
- [ ] Unit tests cover a date just before and just after local midnight, including a timezone that is not UTC.

# Notes

Depends on nothing in S000 except the decision request shape. Can be built beside the addon. Different hours for each child are not part of this story.
