# User Voice

As a parent, I want to know whether a browser extension on the children's computers can reliably report every page
they view, and what installing and keeping it there takes, so that the extension story is built on tested facts
rather than guesses.

# Behaviour

## Findings

- [ ] `docs/browser-extension-spike.md` answers each question in "Questions" below, with what was tried, on which
  browser and version, and what was seen. Where an answer is "not possible", it says what was tried.
- [ ] The findings end with a recommendation for S034.2: the browsers covered, the install and lock-down method, the
  reporting path into daywarden, what is reported for each page view, how a missing or disabled extension is noticed,
  and a size in points.

## Prototype

- [ ] A prototype extension in `extension/` loads in Firefox and in Chromium on an Arch Linux computer, by the
  temporary or developer load each browser offers, and the findings say how.
- [ ] With the prototype loaded, opening a YouTube video and then clicking from video to video, and back, records one
  page view per video with its full address, such as `https://www.youtube.com/watch?v=abc123`, its title, and the
  time. The findings say where these were recorded and show a sample.
- [ ] The same check on two more single-page sites the children use and on an ordinary site records the same.

## Questions

- **Events:** which extension events report a tab's address and title on a page load, a change in the address without
  a page load, and Back and Forward, in each browser, and how titles that update after the address are handled.
- **Time on page:** whether the extension can tell which tab is in front, whether the window has focus, and whether the
  computer is idle, so that a page view could carry the time it was actually on screen.
- **Install and lock-down on Arch Linux:** how Firefox's `policies.json` can force-install the extension so the child
  cannot remove or disable it, given that release Firefox installs only signed extensions, and what signing it as an
  unlisted add-on involves. How Chromium's managed policy can force-install it from a file or address daywarden serves.
  Whether each browser runs it in private and incognito windows, or whether those windows can be turned off by policy.
  The policies already in `docs/child-computer.md` are the starting point.
- **Reporting path:** how the extension sends page views to daywarden so that the computer is identified as the proxy
  identifies it, by address, such as through the proxy to a name the proxy answers itself, and what that means for
  extension permissions. Whether reports should be kept and sent later when daywarden is down.
- **Trust:** whether anyone on the computer could send false page views, and whether that matters.
- **Missing extension:** how daywarden can notice a computer that makes browser requests but sends no page views or
  heartbeat, and what it could do, such as warn the parent or apply a rule.
- **YouTube's own reports, for comparison:** whether the request rows of S030.3 already hold YouTube's playback
  statistics requests, such as `/api/stats/watchtime`, with the video in the query string, and what they would give
  that the extension does not.

# Notes

## Scope

- The prototype is throwaway. It need not be signed, locked down, or report into daywarden's database. A log the
  findings can quote is enough.
- Firefox is the children's main browser and Chromium is also set up, per `docs/child-computer.md`. Other browsers are
  noted only if found on the computers.
- Script injection by the proxy is not tried. See S034's Notes.

## Sizing

5 points: two short prototypes sharing most of their code, tested on a few sites, and the install and policy trials on
the children's computers. Most of the effort is trying things and writing down what happened.
