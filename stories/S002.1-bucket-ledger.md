Title: Bucket ledger

# User Voice

As a parent, I want a two-hour YouTube limit to stay two hours even if we later change how finely we measure it, and I want one stray request at the start of a bucket not to wipe out the rest of that bucket.

# Use Cases

- The bucket length is configurable. The default is five minutes. It is not part of the quota.
- A group's quota is the duration from S001.5. This ledger reports consumed time by adding up ended buckets. It does not store the quota as a bucket count, and it does not divide the duration by the bucket length and save the result.
- An observation is matched to a site group the same way a decision is. Traffic that matches no group, and no default group, is ignored.
- The observation marks the bucket that contains its timestamp, for that client and group, and adds its byte count to that bucket. The bucket stores the length that was configured when it was opened.
- A marked bucket contributes that stored length to the consumed time only when the current time is at or past the bucket's end.

# Acceptance Criteria

- [ ] An observation at 15:00:01 marks the bucket that started at 15:00:00. At 15:04:00 that bucket is not yet counted. At 15:05:00 it is counted.
- [ ] A second observation in the same bucket does not create a second counted bucket. Its bytes are added.
- [ ] An observation at 15:06:00 marks the next bucket.
- [ ] Twenty-four ended five-minute buckets on the same local day, for the same client and group, add up to two hours. Twenty-three add up to 115 minutes.
- [ ] Buckets from the previous local day do not count.
- [ ] Changing the bucket length from five minutes to ten minutes changes which new observations share a bucket. A bucket that was already opened still reports the length it stored, which is five minutes. The configured quota is not rewritten.
- [ ] The observation endpoint answers success without blocking the proxy when the URL matches a group, and it does not return an error to the proxy when the URL matches nothing.
- [ ] The quota condition from S001.5 reads this ledger rather than a test double.

# Notes

Depends on S000.3, S001.2, and S001.5. Idle connections produce no observations, which is guaranteed by S000.3, so an open socket alone does not mark a bucket.

The ledger this story writes is the one S001.5 reads. `usage_buckets` is keyed by client, site group, and the household-local start (`started_at`, to the second, offset dropped rather than converted). `day` is that start's local date. `length_seconds` is the length in force when the bucket was opened and is not rewritten. `byte_count` accumulates; a second observation in the same bucket updates that column and does not insert a row. `site_groups.quota_seconds` is the group's duration from `quota`, or NULL when the group has none. It is not a bucket count. `settings.bucket_length` is the current length in seconds and defaults to 300. `PolicyStore.mark_bucket(client_id, group_name, started_at, length_seconds=None, byte_count=0)` opens or updates a row. `PolicyStore.consumed_seconds(client_id, group_name, at)` is what `quota_remaining` reads: the sum of `length_seconds` for that client and group on the local date of `at`, counting a bucket only when `at` is at or past its end. This story still owns alignment, the observation endpoint, and filling those rows from traffic. A row exists only when the bucket contained traffic, so there is no separate active flag.
