# User Voice

As a parent, I want to connect an AI agent to Daywarden by approving it once in the browser, and to choose what agents
may read and change, so that an agent can answer questions about the household without my signing in again every
quarter of an hour.

# Behaviour

## Configuration file

`config/mcp.yaml` holds the MCP settings. It is separate from `policy.yaml` and is not included by it.

- Layout, with the defaults that apply when a field is left out:

  ```yaml
  enabled: true
  access_token: 1h        # how long an access token lasts
  refresh_idle: 30d       # a connection unused this long lapses
  refresh_lifetime: 90d   # a connection lapses this long after it was approved
  activity_days: 90       # how long the activity log keeps an entry
  permissions:
    tasks: [create, read, update]
    attempts: [read]
  ```

- Durations are a whole number with `m`, `h`, or `d`. A class left out of `permissions` has no permissions.
- The permission classes, and the permissions each one has:

  | Class | Permissions | Covers |
  | --- | --- | --- |
  | `household` | read, update | `entry`, `timezone`, `bucket_length` |
  | `client_groups` | create, read, update, delete | client groups and their addresses |
  | `site_groups` | create, read, update, delete | site groups, priorities, and patterns |
  | `time_windows` | create, read, update, delete | time windows and their periods |
  | `quotas` | create, read, update, delete | quotas |
  | `rule_sets` | create, read, update, delete | named rule sets |
  | `tasks` | create, read, update, delete | tasks of every type. Delete is Retire. |
  | `sentence_pools` | create, read, update, delete | parts of speech sentence pools |
  | `attempts` | read | attempts, trends, and figures |
  | `usage` | read | usage minutes, bytes, and requests |

- [ ] With no `config/mcp.yaml`, or with `enabled: false`, `/mcp`, every `/oauth/` address, and both `/.well-known/`
      addresses below answer 404, and the MCP page says the server is off.
- [ ] `dw check` reports each problem in `mcp.yaml`, such as an unknown class `site_group`, a permission the class
      does not have, such as `attempts: [update]`, or a duration of `0h`. `dw reload` with such a file fails and the
      previous MCP settings stay in force.
- [ ] `dw reload` applies a hand edit of `mcp.yaml` without a restart and commits it as in S023.1.
- [ ] When the decisions service starts with a `mcp.yaml` that has a problem, the service still starts, the MCP
      server stays off, and the MCP page shows the problem.

## MCP page

- [ ] The sidebar has a Settings group holding MCP Server, which opens `/parent/settings/mcp`. The group behaves as
      the other sidebar groups do.
- [ ] The page has an On switch, the endpoint address to copy, such as `https://garden:8084/mcp`, built from the
      first name in `PARENT_NAMES` and the published policy port, the permission matrix, and the four durations.
- [ ] The matrix has a row for each class and a column for each of Create, Read, Update, and Delete, with a checkbox
      only where the class has that permission. The `attempts` row has only Read.
- [ ] Save, Ctrl+S, the changed marks, and the unsaved-changes prompt work as on a task page. A save writes
      `mcp.yaml`, commits it as a portal save does, and is in force at once without a restart. A refused save lists
      each reason in the status bar.
- [ ] Turning the server on when there is no `mcp.yaml` gives read on every class and nothing else.
- [ ] A matrix change applies to an agent already connected from its next call. It does not have to connect again.
- [ ] Turning the server off and saving ends every connection. Turning it on again needs each agent to be approved
      again.
- [ ] *Added in implementation:* Starting the decisions service with the server off, by `enabled: false` or a
      `mcp.yaml` with a problem, also ends every connection, so turning it on later still needs each agent approved
      again.
- [ ] *Added in implementation:* With a `mcp.yaml` that has a problem, the MCP page lists each problem, offers the
      default settings with the server off, and a save writes those settings over the file.
- [ ] Comments written by hand in `mcp.yaml` are still there after a save from the page.

## Connections

A connection is one approval of one agent. It lasts until it is revoked or lapses.

- [ ] The MCP page lists the connections, each with the agent's name, the parent who approved it, when it was
      approved, when it was last used, and when it lapses: the earlier of `refresh_idle` after last use and
      `refresh_lifetime` after approval.
- [ ] Revoke on a connection asks first, with Cancel as the default, and acts at once. It is not part of the next
      save. That agent's next call is refused, and it opens the browser to be approved again.
- [ ] Replacing a parent's password with `python -m policy.accounts` ends the connections that parent approved, as it
      ends their sessions in S007.1.

## Connecting an agent

Daywarden is its own OAuth 2.1 authorization server, following the MCP authorization specification.

- [ ] In Claude Code, `claude mcp add --transport http daywarden https://garden:8084/mcp` followed by `/mcp` opens the
      browser at the consent page. After the parent approves, Claude Code shows the server as connected and lists
      its tools. No token is copied by hand.
- [ ] `/mcp` with no token, an expired token, or a revoked one answers 401 with
      `WWW-Authenticate: Bearer resource_metadata="https://garden:8084/.well-known/oauth-protected-resource/mcp"`.
- The addresses: protected resource metadata (RFC 9728) at `/.well-known/oauth-protected-resource/mcp`, authorization
  server metadata (RFC 8414) at `/.well-known/oauth-authorization-server`, `/oauth/register` (RFC 7591),
  `/oauth/authorize`, `/oauth/token`, and `/oauth/revoke` (RFC 7009), all on the HTTPS parent port.
- A client registers by Dynamic Client Registration or by a Client ID Metadata Document, an HTTPS `client_id` whose
  document the service fetches. A registration that is never approved is removed after 24 hours.
- Only the `code` response type with PKCE `S256` is accepted. The grants are `authorization_code` and
  `refresh_token`. The `resource` parameter must be the `/mcp` address.
- [ ] The consent page, `/parent/settings/mcp/connect?request=<id>`, is a portal page. With no session, signing in
      returns to it. It shows the agent's name, its client id, the address it returns to, and the permissions the
      matrix grants now. Approve sends the browser to the agent's return address with a code. Deny sends it there
      with `error=access_denied`. Both buttons wait for the parent; nothing is approved by loading the page.
- [ ] An authorization request with no PKCE `S256`, with a return address the client did not register, or with an
      unknown request id shows the problem on the consent page and never sends the browser anywhere.
- [ ] *Changed in implementation:* The consent page cannot be shown in a frame on another site. Its response, like
      every portal page's, carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`.
- [ ] A code works once, and only within 1 minute. Using it a second time fails and ends the connection it made.
- [ ] With `access_token: 2m`, the agent keeps working past 2 minutes by refreshing, without opening the browser.
      Each refresh returns a new refresh token. Using an old refresh token again ends the connection.
- [ ] With `refresh_idle: 5m`, a connection unused for 5 minutes lapses, and the agent opens the browser to be
      approved again. With `refresh_lifetime: 10m`, a connection used every minute still lapses 10 minutes after it
      was approved.
- [ ] The portal's session cookie is not accepted at `/mcp`, and an MCP access token is not accepted under
      `/parent/api/`.
- [ ] A request to `/mcp` with an `Origin` header other than the service's own address is refused with 403.
- Access tokens, refresh tokens, and codes are 256 bits from the operating system's random source, and only their
  SHA-256 is stored, as with session keys in S007.1.
- `docs/parent-portal.md` adds the consent page's Approve and Deny as the one place the portal sends the browser to an
  address outside the portal.

## Tools

- [ ] The tool list an agent sees holds only the tools the matrix allows now. With only `tasks: [read]`, Claude Code
      lists `list_tasks` and `get_task` and nothing else.
- [ ] A call to a tool the matrix no longer allows, such as after Read on tasks is unticked mid-session, returns an
      error naming the permission it needs, such as "This needs tasks: read.", and the activity log shows it refused.
- [ ] Each read tool gives the same figures as its portal page for the same choices. `list_attempts` for `younger`
      over the past month gives the same overview rows and attempts as `/parent/attempts` for `younger` with Past
      month, and `get_usage` in minutes by host for today matches the usage graph for the same choices.
- [ ] Times in answers are household-local, as on the portal pages. A period is one of the portal's ranges, such as
      `past_week`, or a `from` and `to` date as `yyyy-mm-dd`.
- The read tools:

  | Tool | Needs | Gives |
  | --- | --- | --- |
  | `get_household` | household: read | `entry`, `timezone`, `bucket_length`, and the household's date and time now |
  | `list_client_groups` | client_groups: read | each client group and its addresses |
  | `list_site_groups` | site_groups: read | each site group, its priority, and its patterns |
  | `list_time_windows` | time_windows: read | each time window and its periods |
  | `list_quotas` | quotas: read | each quota's time, bytes, grace, and rule set |
  | `list_rule_sets` | rule_sets: read | each rule set's rules in order |
  | `list_tasks` | tasks: read | every task, as Task Administration lists them |
  | `get_task` | tasks: read | every field the task's page shows, with a spelling task's words and the pool each is in (*changed in implementation*: every pool, not only current) |
  | `list_sentence_pools` | sentence_pools: read | each pool's id, name, sentence count, and the tasks using it |
  | `get_sentence_pool` | sentence_pools: read | a pool's sentences and their marked words |
  | `list_attempts` | attempts: read | the overview and attempts of `/parent/attempts` (S035.1), with its filters |
  | `get_task_trend` | attempts: read | a task's trend page (S035.1) |
  | `get_arithmetic_facts` | attempts: read | an operation's facts page (S035.2) |
  | `get_attempt` | attempts: read | one attempt's page |
  | `get_usage` | usage: read | the usage graph in minutes or bytes (S030.1, S030.2), with its filters |
  | `list_requests` | usage: read | the request table (S030.3), with its filters |

## Activity log

- [ ] `/parent/settings/mcp/activity`, linked from the MCP page, lists newest first each write, each refused call,
      and each connection approved, revoked, or lapsed. An entry shows the time, the agent, the parent who approved
      it, the tool, what it named, such as `arithmetic/times-7`, and the outcome with any reasons. Reads that succeed
      are not listed.
- [ ] An entry older than `activity_days` is removed.

# Notes

Depends on S007.4 and S035.2. S035.3 to S035.5 each add a read tool for their own figures when they are built, under
`attempts: read`.

The official Python `mcp` SDK serves streamable HTTP and can be mounted in the FastAPI app. A stateless server that
answers each POST with JSON, without server-sent events, is enough, since no tool streams. Pin it in
`policy/requirements.txt`. Authlib, or a small hand-written server, can supply OAuth. Whichever is chosen, the
Change Summary says why.

The MCP page's endpoint address, and the address in the metadata, use the published port, not the bind port 8443,
for the same reason task URLs do.

Sized at 21. The OAuth server, its consent page, and its metadata are larger than the sign-in and certificate work
of S007.1 (5). The settings page, the activity log, and sixteen read tools over existing reports are about one S035
child (13). Kept as one story because the OAuth server, the first risky part, cannot be accepted without a page to
turn it on and a tool to call.

## Change Summary

The MCP endpoint uses the official Python SDK's low-level server, in stateless mode with JSON responses. A new
session manager is made for each POST and run for that request alone, so the SDK needs no application lifespan and
none was added. GET and DELETE answer 405 before the SDK, because the SDK holds a stateless GET open as an event
stream. The bearer check, the `Origin` check, and the 404 while off all happen before the SDK, and the connection is
handed to the tool handlers in a context variable. The SDK runs on the event loop thread, where the SQLite connection
lives. Its pinned version brings in about a dozen packages, including `httpx2`, `jsonschema`, and `PyJWT`, none of which
Daywarden calls.

The OAuth server is hand-written rather than taken from Authlib. Authlib's server side needs its own framework glue,
grant classes, and storage models, and still leaves the consent page, Client ID Metadata Documents, refresh-token
reuse detection, and lapsing to be written. Daywarden needs only public clients, one response type, and two grants,
which is a few hundred lines that sit directly on the store. Tokens and codes follow S007.1's session keys.

Addresses given to agents, in the metadata and the 401 header, use the host the agent asked for when it is one of
`PARENT_NAMES`, and the first name otherwise, with the published port. So an agent added as `https://localhost:8084/mcp`
on the server itself gets a matching issuer, which OAuth clients check. The resource an agent names may be the `/mcp`
address under any parent name.

A connection is made when its code is exchanged, not when the parent approves, so an approval the agent never
completes leaves no connection. Its approval time is the moment Approve was pressed. Every `/mcp` call and every
refresh counts as use for `refresh_idle`. Lapsed connections are found when the server is next used or the MCP page or
log is opened, and the log entry is dated when the connection lapsed.

A save from the MCP page changes only the lines whose values change, through the same text editing the task pages use.
A portal task save reloads the policy without reading `mcp.yaml` again, so a hand edit of `mcp.yaml` with a problem
does not block task saves. `dw reload` reads both, and refuses both.

Reads that succeed are not logged, as the story says. Tool calls refused by the matrix, and calls to a tool that does
not exist, are. A read tool that fails for a reason such as an unknown task returns an error to the agent and is not
logged.

The whole flow was run end to end with curl against the app under uvicorn over TLS: discovery, registration,
authorize, the consent data and its headers, Approve, the token exchange, initialize, the tool list, and a tool call.
Claude Code itself was not connected, and the pages were checked in jsdom only, not in a browser.

## Suggested Acceptance Testing

### Acceptance test cases for S036.1

Rebuild and start with `dw restart`. Claude Code's machine needs `NODE_EXTRA_CA_CERTS` pointing at the household CA.

1. **Connecting Claude Code.** At `/parent/settings/mcp`, with no `mcp.yaml`, check the page says off and the matrix
   offers read on every class. Turn the server on and save, and check `mcp.yaml` and its commit. Run `claude mcp add
   --transport http daywarden https://garden:8084/mcp`, then `/mcp`. Sign in when the consent page asks, check the
   agent, client id, return address, and permissions, and Approve. Check Claude Code lists the tools, then ask it for
   today's household date and younger's attempts over the past month, and compare with `/parent/attempts`. Covers
   Connecting an agent, the MCP page's switch and endpoint, Tools, and the first-time permissions.
2. **Permissions mid-session.** Untick Tasks Read and save. In Claude Code, ask for a task: check the error "This needs
   tasks: read." and the refused entry in the activity log. Reconnect and check `list_tasks` and `get_task` are gone,
   then tick them again. With only `tasks: [read]`, check only those two tools are listed. Covers Tools and the matrix
   applying from the next call.
3. **Lapsing and refresh.** In `mcp.yaml`, set `access_token: 2m` and `refresh_idle: 5m`, and `dw reload`. Use the agent
   for several minutes and check it keeps working. Leave it 6 minutes and check it opens the browser again. Then set
   `refresh_lifetime: 10m`, approve again, use it every minute, and check it lapses at 10 minutes. Check the lapsed
   entries in the log. Covers the lapse and refresh checks and `dw reload` of a hand edit.
4. **Revoking and ending.** Revoke a connection from the page: check Cancel is the default and the agent's next call
   opens the browser. Replace your password with `python -m policy.accounts` and check the same. Turn the server off
   and save: check `/mcp`, the `/oauth/` addresses, and both `/.well-known/` addresses answer 404, and that turning it
   on again needs approval again. Covers Connections and turning the server off.
5. **Bad files.** Write `site_group: [read]`, `attempts: [update]`, and `access_token: 0h` into `mcp.yaml`. Check `dw
   check` lists all three and `dw reload` fails with the previous settings still in force. `dw restart`, and check the
   service starts with the MCP server off and the page lists the problems. Covers the Configuration file checks.
6. **The page as an editor.** Add comments to `mcp.yaml`, change a duration and two checkboxes on the page, and check
   the changed marks, Unsaved changes, the leave prompt with Stay as default, Ctrl+S, and that the comments are still
   in the file. Save with `0h` and check the status bar lists the reason. Covers the MCP page's editing checks.
7. **Refusals in the sign-in.** With curl, check `/mcp` with no token, a made-up token, and the portal cookie each answer
   401 with the `WWW-Authenticate` header, an `Origin: https://evil.example` answers 403, and the access token is
   refused under `/parent/api/`. Open `/oauth/authorize` with no `code_challenge`, with a `redirect_uri` the client did
   not register, and the consent page with `request=nonsense`, and check each shows the problem with no buttons.
   Exchange a code twice and check the connection is gone. Check the consent page's response headers. Covers the
   remaining Connecting an agent checks.
8. **The other read tools.** Grant read on every class and ask the agent for each of the client groups, site groups,
   time windows, quotas, rule sets, a spelling task, a sentence pool, a task trend, the multiplication facts, one
   attempt, usage in minutes by host for today, and the request table, and compare each with its page. Covers the
   rest of Tools.
