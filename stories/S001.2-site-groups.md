# User Voice

As a parent, I want to put websites into named groups with a priority order, so that Classroom is recognized before a general Google rule, and so that everything else falls into a default group.

# Use Cases

- Create any number of groups. Each group has a unique priority. Lower priority is tested first.
- A group has a list of glob patterns.
- A pattern containing `://` is matched against the absolute URL with the fragment removed.
- A pattern without `://` is matched against the host only, so `*.youtube.com` and `youtu.be` work.
- Matching is case-insensitive. `*` matches across slashes. `?` matches one character.
- Exactly one group may be marked as the default. It is used only when no earlier group matches. Its patterns are ignored.
- A request that matches nothing, when no default group exists, is denied.

# Acceptance Criteria

- [x] For a URL that matches two groups, the lower priority number wins.
- [x] `https://classroom.google.com/u/0/h` matches `https://classroom.google.com/*` and `classroom.google.com`.
- [x] `https://www.youtube.com/watch?v=abc#t=10` matches `*.youtube.com` and does not use the fragment.
- [x] `https://www.youtube.com/watch?v=abc` does not match `*.googlevideo.com`.
- [x] Host matching ignores case in both the URL and the pattern.
- [x] Two groups with the same priority are rejected as invalid configuration.
- [x] Two default groups are rejected as invalid configuration.
- [x] With a default group present, an unrecognized URL is assigned to it.
- [x] With no default group, an unrecognized URL produces a deny decision with a message that says the site is not in a configured group.
- [x] Groups are stored in SQLite and loaded again after a restart.

## Change Summary

Site groups are `[[groups]]` tables in `config/policy.toml`. Each has a `name`, an integer `priority`, an optional `patterns` list and an optional `default = true`. Parsing rejects a repeated name, a repeated priority, a second default group, a priority that is not a whole number (including `true`, `"1"` and `1.5`), empty or non-string patterns, and unknown keys such as `rules`. Groups are written into SQLite in the same transaction as the timezone and clients.

`policy/groups.py` holds the matcher. A pattern with `://` is matched against the lower-cased URL with its fragment removed. Any other pattern is matched against the host from `urlsplit`, which drops the port and userinfo and ignores a trailing dot. `*` becomes `.*` (so it crosses `/`), `?` becomes one character, and everything else is literal. The pattern must match the whole string, so `*.youtube.com` does not match bare `youtube.com`, and `youtube.com` does not match `example.org/youtube.com`. Compiled patterns are cached. `SiteGroups.classify` tries the non-default groups in ascending priority and returns the default group, or `None`, when nothing matches.

The default group is always tried last, whatever its priority number, and its patterns are ignored. That is my reading of "used only when no earlier group matches". Every group still needs a unique priority, including the default, so the schema stays uniform. The sample uses 1000 for the default.

The schema moves to version 2. `store.py` now runs a list of migrations, so an existing version-1 `policy-data` volume gains the `site_groups` and `site_group_patterns` tables and keeps its clients. A group keeps its row id while its name stays the same, so the S001.3 rules can attach to it. Unique priority and a single default are enforced at parse time rather than with SQLite constraints. With those constraints, swapping two groups' priorities in one load would hit a transient conflict.

The decision context now carries the site group. `decide()` returns `{"action": "deny", "status": 403, "message": "This site is not in a configured group."}` for a URL in no group. Otherwise it still returns `config/decision.json` until S001.3 adds the rule engine. The decision log entry has a new `"group"` field (the name, or `null`). The service prints each group on start, says so when there is no default group, and adds the group name to each decision line in `docker compose logs decisions`.

The behaviour change to watch: a database with no groups at all has no default, so every site is denied. The sample `config/policy.toml` therefore ships a single `Everything else` default group, plus a commented example. The S000 integration fixtures each write a one-line default group. S001.6 replaces the sample groups with the real household set.

## Suggested Acceptance Testing

- Run `python -m pytest tests/test_policy_groups.py tests/test_policy_decisions.py tests/test_policy_clients.py`. No Docker is needed. These cover the matcher cases from the acceptance criteria, priority order, the default group, every invalid-configuration case, reopening the database, and upgrading a version-1 database.
- Run `python -m pytest tests/test_policy_service.py`. It configures two groups and no default, checks that YouTube and Classroom land in the right groups and that `https://example.org/` gets the "not in a configured group" deny, then recreates the container without the file and checks all of that again.
- Upgrade check on your real stack: run `make up` against the existing `policy-data` volume. The service should start cleanly and log `group Everything else: default`. Your stored clients should still be listed.
- Add a group to `config/policy.toml`, for example `name = "Entertainment"`, `priority = 30`, `patterns = ["*.youtube.com", "youtu.be"]`, then `docker compose restart decisions`. Browse to YouTube and run `docker compose exec decisions tail -n 3 /tmp/decisions.jsonl`. Expect `"group": "Entertainment"`. Other sites should show `"group": "Everything else"`.
- Comment out the `Everything else` group and restart. The log should warn `no default group`. A site outside your groups should show the 403 page "This site is not in a configured group.", while YouTube still gets `config/decision.json`.
- Give two groups the same priority, or mark two groups `default = true`, and confirm `make up` fails loudly with the error in `docker compose logs decisions`.
- Known, and not from this story: two tests in `tests/test_run_proxy.py` fail because they use the repo's own `config/`, whose committed `decision.json` is a deny. Requests now reach the sample's default group first, and then get that same deny.
