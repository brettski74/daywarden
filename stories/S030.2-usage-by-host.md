# User Voice

As a parent, I want to open a line on the usage graph and see which hosts it was spent on, in minutes and in bytes
each way, so that I can tell whether the entertainment time last week was YouTube, a game, or something I have not met
yet.

# Behaviour

## Host bar chart

- [ ] Double-clicking a line on the S030.1 graph, or pressing Enter on its legend entry, opens a bar chart beneath the
  graph with the shared expand animation. Its heading names the line and the range, such as
  `younger, Past week: top hosts`.
- [ ] The bar chart lists hosts down the left with a bar to the right for each, and the value at the end of the bar. It
  shows at most 20 hosts, the highest first. It covers the line's group within the same filters and range as the
  graph, in the page's unit.
- [ ] A host is the host name from the address fetched, with the port only when the address named a port other than the
  scheme's default, such as `www.youtube.com` or `localhost:3000`. Browsers drop `:443` from an `https` address and
  `:80` from an `http` one, so those are never shown.
- [ ] On the Minutes page, a host gains a bucket's length once for each bucket in which it sent or received any bytes,
  however many requests it served in that bucket. For example, a page whose HTML, three stylesheets, four scripts, and
  two images all come from `www.example.com` within one three-minute bucket gives `www.example.com` three minutes, not
  thirty. Another host used in the same bucket also gains those three minutes, so the bars can add up to more than the
  line. A line that covers several groups or quotas adds them, as in S030.1.
- [ ] On the Bytes page, each bar is split into downloaded and uploaded, told apart by colour and named in a key, with
  both figures at its end, such as `1.2 GB down, 40 MB up`. Hosts are ordered by the two added together.
- [ ] Double-clicking another line replaces the bar chart. A close button collapses it with the shared animation.
- [ ] The line drilled into is in the page address, so Reload, Back, and a bookmark open the bar chart too. Changing a
  filter or the range redraws both charts.
- [ ] A range that starts before the oldest host detail kept says from when it is kept, such as
  `Hosts are kept for 30 days, from Wednesday 14 October 2026.`, and shows the hosts from then on. Before the upgrade,
  that date is the day of the upgrade.
- [ ] The S030.1 graph is unchanged by the upgrade and by the retention. Its totals still reach back to the install.

## Retention

- [ ] `host_retention` in the policy file sets how long host detail is kept, in whole days, such as
  `host_retention: 30d`. Left out, it is 30 days. A value that is not a whole number of days of at least one is a
  load error that names the key, and the policy in force stays.
- [ ] Host detail older than the retention is deleted at least once an hour, and when the service starts. The bar chart
  never shows anything older. Shortening the retention and running `dw reload` removes the older detail within the
  hour.

# Notes

## Design hints

- **Host buckets.** Two new tables beside the existing ones, such as `host_buckets` keyed by client group, site group,
  host, and bucket start, and `host_quota_buckets` keyed by client group, quota, host, and bucket start. Each holds the
  bucket's length, bytes down, and bytes up. `UsageStore.file_observation` writes them in the same transaction as the
  existing rows, with the same bucket placement and the same quotas. A second report for the same host in the same
  bucket adds bytes to the row and does not add time, which is what counts a page's ten requests once.
- **Why not match requests to buckets by time.** Counting the buckets that overlap any request to the host would also
  count buckets in which a connection was open but idle, such as a long poll or a paused video, and it needs an
  interval join over a month of requests on every drill-down. Recording the host when its bytes are filed counts a
  bucket only when that host moved bytes in it, which is how the site-group time is already counted, and the query is a
  plain sum.
- **The proxy.** Today one meter counts the request and response bodies of a flow together. It needs one meter per
  direction, and each report carries `bytes_up` and `bytes_down`, with `bytes` still the total the existing ledger
  files. The observations service takes the host from the URL it already receives. A report from an older proxy with
  only `bytes` is filed as downloaded.
- **Size.** At a 3m bucket and about 40 hosts a bucket, four hours a day is about 3,000 rows a day for each client
  group, under 100,000 in 30 days.
- The bar chart is a horizontal stacked bar chart in the S030.1 chart kit, using `d3-shape`'s stack.
- The retention lives in `policy/hierarchy.py` beside `bucket_length`. The observations service, which writes the
  rows, deletes the old ones.

## Out of scope

- Grouping hosts under one site. YouTube's video comes from many `*.googlevideo.com` hosts, such as
  `rr3---sn-ab5l6nrz.googlevideo.com`, which each get their own bar. The site group line already gives YouTube's total.
  A later story could group the bars by registrable domain.
- Upload and download apart on the S030.1 graph.

## Sizing

13 points: the proxy's two meters and the new report fields, the host bucket tables and their writes, the retention
setting and the deletion, the endpoint for the top hosts, and the bar chart and its place in the page address. The
graph and filters are reused from S030.1.
