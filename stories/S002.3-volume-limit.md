# User Voice

As a parent, I want a way to cap how much data a site group can move in a day, so that downloading a pile of videos inside the time quota is not a way around the limit.

# Use Cases

- A group may set an optional daily byte limit beside its time quota.
- A new rule condition `volume_remaining` is true while today's observed bytes for that client and group are under the limit.
- The sample entertainment policy does not enable this condition until a parent turns it on. The first version of the household can run with time buckets only.

# Acceptance Criteria

- [x] Bytes already stored by S002.1 are what the condition reads. There is no second metering path.
- [x] A group with no byte limit makes the condition true.
- [x] Crossing the limit makes a rule that denies on false return `403` with that rule's message.
- [x] The usage report shows the day's byte total next to the limit when one is set.
- [x] This story is implemented only after a parent has looked at real YouTube byte totals from S002.2 and chosen a starting limit. The story record notes the totals that justified the number.

## Change Summary

A group may set `byte_limit`, a size such as `500MB`, `1GB`, `1000KB`, or `1000B`. `1KB` and `1000B` are 1,000 bytes. `1MB` is 1,000,000. A bare number is rejected. The value is stored on `site_groups.byte_limit`, NULL when the group has none. Schema version 6 adds that column. A version-5 database keeps its groups, its quota, and its buckets, and the new column is NULL.

`volume_remaining` is true while today's stored bytes for this client and this group are strictly under that limit. The total is `SUM(byte_count)` on `usage_buckets` for that client, group, and household-local day. An open bucket is included, which is the point of the cap: a download inside the current bucket has already moved those bytes, even though the time quota does not count the bucket until it ends. Yesterday's rows, another client's rows, and another group's rows are left out. A group with no byte limit makes the condition true. There is no second meter. Observations still call `mark_bucket`, and changing the stored `byte_count` is what changes the decision.

A rule that denies when the condition is false returns `403` with that rule's message. In the sample, the Entertainment quota rule allows when time remains, which stops the list, so a volume rule written after that allow would never run. The README shows the shape that reaches it: `quota_remaining` continues when time remains, and `volume_remaining` allows or denies. The sample does not use that shape. Entertainment stays `quota = "2h"` with no `byte_limit`.

The usage report, when a limit is set, names it (`Byte limit: 2 MB.`) and each day shows that day's stored bytes beside it (`Bytes: 1,147 bytes of 2 MB.`), including a bucket that has not ended. A day with no traffic still says no usage, and shows zero bytes of the limit. A group with no limit is unchanged.

The decisions service reads the ledger on the same path as the time quota. Its startup line for a group with no cap ends in `no byte limit`.
