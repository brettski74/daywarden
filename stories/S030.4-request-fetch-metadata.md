# User Voice

As a parent, I want to filter the request table so that what I see is mostly the pages the child chose to open, not the
dozens of images, scripts, stylesheets, frames, ads, and scripted fetches that a single page load can spawn, so that a
list of requests is useful for seeing where they went rather than a sea of subordinate noise.

# Behaviour

## Stored metadata

Each request row keeps five Fetch Metadata request headers when the browser sent them: `Sec-Fetch-Dest`,
`Sec-Fetch-Mode`, `Sec-Fetch-Site`, `Sec-Fetch-User`, and `Sec-Purpose`.

- [ ] The request table of S030.3 gains the columns Dest, Mode, Site, User, and Purpose, after Method, holding each
  header's value as the browser sent it. For example, `curl -x ... --cacert ... -H 'Sec-Fetch-Dest: image' -H
  'Sec-Fetch-Mode: no-cors' -H 'Sec-Fetch-Site: cross-site' https://www.example.com/a.png` lists `image`, `no-cors`,
  and `cross-site`, with User and Purpose blank.
- [ ] A header the browser did not send is a blank cell, never a guessed value. A plain `http` page in Firefox, a
  `curl` request with no `-H`, and every request recorded before this story have all five blank.
- [ ] In Firefox on a child computer, typing `https://www.example.com/` in the address bar lists a row with Dest
  `document`, Mode `navigate`, Site `none`, and User `?1`, and the page's images and scripts list as `image` and
  `script` with User blank. Clicking a link on that page lists the new page with Site `same-origin`, `same-site`, or
  `cross-site` and User `?1`.
- Clicking a heading sorts by these columns as by any other, with blank cells first when ascending.

## Fetch filter

The Fetch pull-down chooses one of three levels. Each level's label names its rule in the browser's own terms:

- **All requests**: every request, as in S030.3.
- **Documents (Sec-Fetch-Dest: document)**: requests with `Sec-Fetch-Dest: document` whose `Sec-Purpose` does not
  name `prefetch`, and requests with no `Sec-Fetch-Dest` that are a page load by the plain `http` rule of S015: a
  `GET` whose `Accept` includes `text/html`.
- **User-activated documents (Sec-Fetch-User: ?1)**: Documents that also carry `Sec-Fetch-User: ?1`. Plain `http`
  page loads carry no `Sec-Fetch-User`, so they are not listed at this level.

- [ ] The Fetch pull-down sits with the Host box and Outcome on the Requests page, and above the table in the host
  drill-down. All requests is the default on both. Changing it returns to the first page.
- [ ] Documents lists the example.com page load above but not its images or scripts, nor `iframe`, `empty`, `style`,
  `font`, or `script` requests from any site. `curl -x ... -H 'Accept: text/html' http://<allowed host>/` is listed;
  the same with curl's default `Accept: */*` is not.
- [ ] Documents leaves out speculative loads. `curl -x ... --cacert ... -H 'Sec-Fetch-Dest: document' -H
  'Sec-Purpose: prefetch;prerender' https://www.example.com/next` is listed under All requests and not under Documents.
- [ ] User-activated documents lists the typed and clicked pages above, and leaves out a page that a script or a meta
  refresh moved to on its own, which has no `Sec-Fetch-User`. `curl -x ... --cacert ... -H 'Sec-Fetch-Dest: document'
  https://www.example.com/` is a Document but not a User-activated document; adding `-H 'Sec-Fetch-User: ?1'` makes it
  both.
- [ ] Refused requests follow the same rule as allowed ones. A page load of a host the policy denies or redirects is
  listed under Documents, and a refused `Sec-Fetch-Dest: image` request to that host is not.
- [ ] Hide redirect hops is a checkbox beside the Fetch pull-down, shown only when Documents or User-activated
  documents is chosen, and checked when either is first chosen. While checked, an allowed request with a 3xx status is
  left out, so clicking a Google search result lists the page it lands on but not `www.google.com/url`. A request the
  policy redirected, with outcome redirected, is still listed.
- [ ] The level and the checkbox are in the page address with the other filters, so Reload, Back, and a bookmark open
  the same list. They are not part of a preset, as with the Host box and Outcome.
- [ ] In the drill-down, changing the Fetch pull-down or the checkbox narrows the open table and does not close it. The
  graph's own filters still close it as in S030.3.

## Household documentation

- [ ] `docs/hierarchical-policy.md`, beside the request rows and `request_retention`, describes the five columns, the
  common values of each, and the three levels, and states what the levels cannot show: pages a single-page site such
  as YouTube changes to without loading a new page, pages a service worker answers from its cache, and requests from
  before this story. It says the lists are much likelier to be pages the child opened, not an exact address-bar
  history.

# Notes

## Why this sits under S030

S030.3 already lists every request. Without a way to favour navigations, that list is dominated by subordinate fetches.
This child adds only metadata and filtering on that table. It does not change the Minutes or Bytes graphs or the host
bars, which still count every request.

## Design hints

- `proxy/addon.py` `_ask` already sends `Sec-Fetch-Dest` and `Accept` as `sec_fetch_dest` and `accept`. Add
  `sec_fetch_mode`, `sec_fetch_site`, `sec_fetch_user`, and `sec_purpose` the same way, and accept them as optional
  strings in `parse_request` in `policy/decisions.py`. Browsers send `Sec-Fetch-*` only to `https` and other trustworthy
  origins, so plain `http` relies on `Accept`.
- The Documents rule for rows with no `Sec-Fetch-Dest` is `is_page_load` in `policy/returns.py`. Store either `Accept`
  or the result of that rule on the row when it is written, so the filter does not need the whole header later.
- The `requests` table in `policy/usage.py` is created with `CREATE TABLE IF NOT EXISTS`, and nothing alters an existing
  table yet. Existing households need the new columns added on start, checked with `PRAGMA table_info`.
- Filtering by level adds a condition to the existing range scans. Consider whether the Requests page's Documents
  levels need an index on start time and Dest, given about 600,000 rows over 30 days.
- No backfill is possible. The decision log is `/tmp/decisions.jsonl` inside the decisions container and does not
  survive a restart.
- Hide redirect hops leaves out allowed 3xx rows only. Policy redirects have the outcome redirected and status 302 and
  stay listed.

## Known limits

- Single-page sites such as YouTube, TikTok, and Reddit change the address with scripted fetches after the first page
  load, so the Documents levels show only the first page of such a visit. S034 looks into a browser extension that
  reports those page changes.
- Chrome may prerender a page while the child types in the address bar. If the child then opens it, the prerender is
  the only request, so Documents leaves out that visit.

## Out of scope

- Reporting page changes inside single-page sites, which is S034.
- Changing the page a site serves, such as adding a script, to observe navigation.
- Reconstructing which page element or script caused a request.
- Changing how host buckets or the usage graph count time and bytes.
- A pull-down of raw `Sec-Fetch-Dest` values. The columns sort, and the levels cover the use the story is for.

## Sizing

13 points: four more headers from the proxy, the column upgrade of an existing table, the five columns, the Fetch
levels and hop checkbox on both views with their address handling, and the household documentation. Larger than the
earlier guess of 8 because Mode, Site, User, and Purpose are now stored and the drill-down gains its own control.

## Change Summary

The proxy forwards four more Fetch Metadata headers, and each request row stores all five as sent, NULL when absent.
When the row is written, the Documents rule is decided once and stored as `page_load`: `Sec-Fetch-Dest: document` with
no `prefetch` item in `Sec-Purpose`, or, with no `Sec-Fetch-Dest`, the `is_page_load` rule of `policy/returns.py` (a
`GET` accepting `text/html`). So `Accept` itself is not stored. A `Sec-Fetch-Dest: document` request counts whatever
its method, as the story states the rule, so a form post that opens a page is a Document. Rows from before this story
have `page_load` 0 and so only appear under All requests.

Existing databases gain the columns with `ALTER TABLE ... ADD COLUMN` on start. The policy and observations services
share the file, so a "duplicate column" error from the other one adding it first is ignored. The Documents levels add
`page_load = 1` to the range scan, and the new `(page_load, started_at)` index serves it as a covering index search,
so the levels do not scan the whole 30 days of rows.

In the address, `fetch=documents` or `fetch=user` names the level, and Hide redirect hops is checked unless
`hops=show`. That makes choosing a documents level from All requests check the box, and moving between the two
documents levels keep it as it is. Hidden hops are allowed rows with a 3xx status. A row still running, with no
status yet, stays listed. In the drill-down, opening another host keeps the level; closing the table or changing the
line drops it.

## Suggested Acceptance Testing

### Acceptance test cases for S030.4

Rebuild and start with `make up`. Sign in to the parent pages. Use a child computer with Firefox, and a shell that can
reach the proxy with its CA certificate for the `curl` checks.

1. **Upgrade of an existing household.** Before rebuilding, note a few request rows on Requests. After `make up`,
   check they are still listed with five blank Fetch cells, and are listed only under All requests. Covers the blank
   cells for earlier requests, and the column upgrade.
2. **Firefox browsing.** On the child computer, type `https://www.example.com/`, then click a link, then visit a page
   that uses a meta refresh or script redirect, and a plain `http` page. On Requests, check the Dest, Mode, Site, and
   User values, then each Fetch level. Sort by Dest both ways and check blank cells come first ascending. Covers Stored
   metadata, Documents, and User-activated documents.
3. **curl checks.** Run the `curl` commands in the Behaviour items: the image request, the plain `http` request with
   `Accept: text/html` and with the default `Accept: */*`, the prefetch request, and the document request with and
   without `Sec-Fetch-User: ?1`. Check each level lists them as described. Covers the curl examples in Stored metadata
   and Fetch filter.
4. **Refused requests.** Open a page the policy denies or redirects in Firefox, and send a `Sec-Fetch-Dest: image`
   request to that host. Under Documents, the page load is listed and the image is not. Covers refused requests.
5. **Redirect hops.** Search Google on the child computer and click a result. Under Documents, Hide redirect hops is
   shown and checked; `www.google.com/url` is absent and the landing page is listed. Uncheck it and the hop appears.
   Check a policy redirect stays listed while checked. Switch Documents to User-activated documents and back to All
   requests and watch the checkbox. Covers Hide redirect hops.
6. **Address and presets.** With a level and the checkbox chosen, on page 2, change the level and check it returns to
   page 1. Reload, use Back, and open a bookmark. Change Date range and check the level stays; choose a preset and
   check it does not carry the level. Covers the address and preset items.
7. **Drill-down.** On Minutes, open a line and double-click a host. Above its table choose Documents, toggle the
   checkbox, and check the table narrows and stays open. Then change Date range and check it closes. Covers the
   drill-down item.
8. **Documentation.** Read "Fetch metadata and the Fetch filter" in `docs/hierarchical-policy.md`. Covers Household
   documentation.
