# User Voice

As a parent, I want to filter the request table so that what I see is mostly the navigations the child chose, not the
dozens of images, scripts, stylesheets, frames, ads, and scripted fetches that a single page load can spawn, so that a
list of requests is useful for seeing where they went rather than a sea of subordinate noise.

# Behaviour

## Honest labels

Labels and filter names describe what is stored, not a stronger claim than the data supports. Prefer the browser's own
names, such as `Sec-Fetch-Dest` and its values (`document`, `script`, `style`, `image`, `empty`, and the rest), over a
label like "page loads" when a material share of matching rows may not be top-level address-bar navigations. Household
docs may say which values usually mean a top-level or framed navigation, and which are noisier.

## Stored metadata

- [ ] Each request row keeps the fetch-metadata fields this story settles on, taken from the decision request when the
  browser sent them. A missing field is stored as absent, not invented.
- The first candidate is `Sec-Fetch-Dest`, which the proxy already sends for decisions. Whether `Sec-Fetch-Mode`,
  `Sec-Fetch-Site`, `Sec-Fetch-User`, or others are kept as well is settled in refinement.
- Rows written before this story have no metadata; filtering on it leaves them out or treats them as unknown, as
  refinement chooses.

## Filtering the request table

- [ ] The shared request table (the host drill-down and the Requests page from S030.3) can be narrowed using the stored
  metadata so a parent can cut most subordinate asset and scripted-fetch noise and keep rows that are much more likely
  to be user-triggered navigations (top-level or framed loads from a click or similar), accepting that the cut is
  statistical, not exact.
- Exact controls, defaults, presets, and how unknown or missing metadata is treated are settled in refinement. The
  important outcome is a quieter list biased toward navigations, not a perfect address-bar history.

# Notes

## Why this sits under S030

S030.3 already lists every request. Without a way to favour navigations, that list is dominated by subordinate fetches.
This child only adds metadata and filtering on that table; it does not change the Minutes or Bytes graphs or host bars.

## What the browser already says

Modern browsers send Fetch Metadata request headers on HTTPS. Pages cannot set them. The closest signal for "how will
this response be used?" is `Sec-Fetch-Dest` (for example `document` for a top-level navigation, `iframe` / `frame` for
framed documents, `script`, `style`, `image`, `empty` for `fetch()` / XHR / beacons and similar). `Sec-Fetch-Mode`,
`Sec-Fetch-Site`, and `Sec-Fetch-User` add context. Daywarden already forwards `Sec-Fetch-Dest` and `Accept` on each
decision for the way-back page-load check; this story is about keeping enough of that on the request row for parents to
filter.

There is no header that names the address-bar URL that caused a subresource. Accuracy is "much likelier to be a
navigation the child triggered," not "only what appeared in the address bar."

## Open for refinement

- Which headers to store (Dest alone, or Mode / Site / User as well).
- Column and filter UI on the drill-down and the Requests page; defaults that favour quieter lists without hiding
  refused traffic the parent still needs.
- Whether presets may hold these filters.
- How plain HTTP and other clients with no `Sec-Fetch-*` are shown and filtered.
- Whether the decision log's existing fields are enough for backfill, or only new rows get metadata.
- Story points after the filter surface is fixed (8 is a standing guess).

## Out of scope

- Reconstructing which page element or script caused a request.
- Changing how host buckets or the usage graph count time and bytes.
- Claiming a perfect list of address-bar page views.

## Sizing

Provisional 8 points: persist metadata already available at decision time, expose it on the S030.3 table and filters,
and document honest names. Revisit after refinement if Mode/Site/User and richer defaults expand the surface.
