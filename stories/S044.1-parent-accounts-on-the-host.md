# User Voice

As whoever runs Daywarden, I want one command that adds, changes, lists, and removes parent accounts, where an account
can be added with an email address and no password, so that each parent can later choose their own password and nobody
else ever knows it.

# Behaviour

## The dw-account command

`dw-account` replaces `bin/add-parent` for managing parent accounts on the host. Each action is a subcommand, and each
subcommand says whether its account must be new or must already exist:

- `dw-account add [--role admin|reviewer] [--email ADDRESS] [--password] USERNAME`: adds a new account. `--role`
  defaults to `reviewer`, so an admin is only ever made by asking for one. The account has no password unless
  `--password` is given.
- `dw-account update USERNAME [--role admin|reviewer] [--email ADDRESS | --no-email] [--password]`: changes an existing
  account. It needs at least one switch.
- `dw-account remove [--yes] USERNAME`: removes an existing account.
- `dw-account list` and `dw-account help`.

Each account may have one email address, which only `dw-account` sets or removes.

- [ ] After upgrading, `dw-account list` shows every existing account with its role and "no email". Each one signs in
      with its password as before, and keeps its sessions and the MCP connections it approved.
- [ ] `dw-account add --email nana@example.net nana` adds a reviewer with that address and no password, and asks for
      none. It prints that nana has no password yet and that `dw-account update --password nana` sets one.
      `dw-account add --role admin --password bee` adds an admin with no address and asks for the password.
- [ ] `add` with neither `--email` nor `--password` is refused with a message that the parent would have no way to
      set a password, and nothing is added.
- [ ] `add` for a username that already exists is refused with a message that points to `update`. `update` or
      `remove` for an unknown username is refused with a message that points to `add`. Nothing changes.
- [ ] While there is no admin, as on a fresh install, `add` without `--role admin` is refused with "There is no admin
      yet. Add the first account with --role admin." and nothing is added.
- [ ] `update` with no switch, `--email` with `--no-email`, a switch that does not belong to the subcommand such as
      `list --role admin` or `remove --password`, an unknown subcommand, or a missing username is refused with the
      subcommand's usage, and nothing changes.
- [ ] `dw-account update --email ada@example.net ada` sets Ada's address, `--no-email` removes it, and neither asks
      for a password. An address that is not of the form `name@domain`, such as `ada` or `ada@`, is refused with a
      message, and nothing changes.
- [ ] `dw-account update --role reviewer ada` changes Ada's role as `--set-role` did in S043, with the same refusals,
      such as making the only admin a reviewer, and the same end to her sessions.
- [ ] `--password`, on `add` or `update`, asks for the password twice with echo off. An empty password, one longer
      than 200 characters, or two that differ, is refused, and nothing changes. A password is never read from the
      command line. Without a terminal, it is read once, as one line of standard input. `update --password` ends the account's sessions and the MCP
      connections it approved, as replacing a password did in S007.1.
- [ ] Several switches on one `update`, such as `update --role admin --email nana@example.net --password nana`, are
      all checked first. If any one is refused, nothing changes. Otherwise the command prints each change.
- [ ] Ctrl+C, Ctrl+\\, Ctrl+D, closing the terminal, or `kill` of the command while it waits for a password leaves the
      terminal echoing what is typed, and changes nothing.
- [ ] `dw-account remove nana` asks "Remove nana? This cannot be undone. [y/N]". Only `y` removes the account.
      Without a terminal, it is refused unless `--yes` is given.
- [ ] After `remove`, the account is gone from `dw-account list`. Every tab it has open must sign in again, and signing
      in as it is refused as an unknown username is. The MCP connections it approved end, with "the parent's account
      was removed" in the activity log, and the log's earlier entries still name it. A new account added later with
      the same username gets none of these back.
- [ ] Removing the only admin is refused: "ada is the only admin. Add another admin first." Nothing changes.
- [ ] `dw-account list` shows each account's username, role, address or "no email", and "no password" for an account
      whose password has not been set, in username order. `dw-account help` and `dw-account SUBCOMMAND --help`
      describe every subcommand and switch, and which ones need the account to exist.
- [ ] `dw-account` works from any directory and through its link in `~/bin`, as `bin/add-parent` did. Installing or
      upgrading adds the `~/bin/dw-account` link and removes `~/bin/add-parent`. `bin/add-parent` in a clone or in
      `~/daywarden/bin` prints "add-parent is now dw-account. Run dw-account help." and exits with status 1.

## Signing in

A password is at most 200 characters, counted as Unicode characters, so a password of 200 is accepted. The limit
applies wherever a password is given: `dw-account`, the sign-in screen, and the pages S044.2 adds. It is long enough
for any passphrase, and keeps the service from hashing whatever an attacker sends.

- [ ] Signing in to an account with no password is refused with the same message as a wrong password, and after the
      same delay, for any password, including an empty one. A request sent with `curl` that leaves out the password or
      sends an empty string gets the same refusal. After `dw-account update --password nana`, nana signs in.
- [ ] Signing in with a password longer than 200 characters is refused with the same message as a wrong password, and
      after the same delay, without hashing what was sent. A sign-in request body larger than 4 KB is refused with 413
      before it is read to the end, and changes nothing.

## Documentation

- [ ] `README.md`'s Parent accounts section describes `dw-account` and each subcommand in place of `bin/add-parent`,
      that a new account is a reviewer unless `--role admin` is given, and `remove` for an account whose security is
      in doubt. Every other mention of `add-parent` in `README.md` and `docs/` names `dw-account` instead. The
      installer's closing hint reads "add the first parent with dw-account add --role admin --password USERNAME".

# Notes

- Depends on S007.1 (accounts, sessions, and `bin/add-parent`), S014 (the installed host commands), S043 (roles), and
  S036 (MCP connections that end with a password).
- Decided while refining:
  - `bin/add-parent` becomes `dw-account`, with subcommands, built here as it is meant to stay, so the command line is
    reviewed once. `update` takes the place of S043's `--set-role` and of replacing a password.
  - A new account is a reviewer unless `--role admin` is given, by least privilege. This reverses S043, where a new
    account was an admin.
  - A new account has no password unless the host sets one. Until S044.2, `update --password` is the only way to give
    it one. The host can always set a password, for a household without a mail server.
  - An account whose security is in doubt is removed, not disabled, because keeping its password is rarely wanted,
    and it can be added again. There is no host command to clear a password or to send a reset link. A parent who
    cannot sign in uses Forgot password from S044.2.
  - No email is sent here. S044.2 adds the welcome email on `add`, the notice on `update --password`, and
    `dw-account test-email`.
- Implementation hints:
  - Add a nullable `email` column to `parent_accounts`, upgraded as S043 added `role`. `password_hash` is `NOT NULL`
    today. The service runs SQLite 3.46.1, from Debian in the `python:3.14-slim` image, which cannot drop a
    `NOT NULL` in place, so the upgrade rebuilds the table, keeping each row's `id` so sessions and MCP connections
    still match. The host's `.venv` has SQLite 3.54.0, so a newer `ALTER TABLE` form would pass the unit tests and
    then fail in the container. Test the upgrade through a stack test as well.
  - `login()` already checks the dummy hash for a missing username, so a null hash takes the same path.
  - Removing an account deletes its row, which cascades to its sessions. Delete its `mcp_codes` and end its
    `mcp_connections` through `McpStore.end_for_account`, because neither has a foreign key. `mcp_activity` keeps the
    username as text, so its entries stay.
  - `dw-account` runs `python -m policy.accounts` in the decisions container, as `bin/add-parent` did. Use `argparse`
    subparsers.
  - `getpass` restores echo on Ctrl+C but not on SIGTERM or SIGHUP. Turn those into an exception while the prompt is
    open, so its `finally` runs, or restore the saved `termios` state in a handler. The prompt runs inside the
    container's terminal under `docker exec -it`, so test the signals there as well as in a unit test.
  - The stack tests that pipe a password into `add-parent`, in `tests/test_dw.py`, `tests/test_install_stack.py`, and
    `tests/test_reload_stack.py`, use `dw-account add --password` instead.
- Out of scope: disabling an account without removing it, a portal page for managing accounts, a minimum password
  length, and any email.
- Sizing: 8 points, against S043's 13. It replaces the command with subcommands, rebuilds the accounts table for a
  nullable password, and adds `remove` with its MCP clean-up, the signal handling, and the installer's link change.
  There are about 17 checks, all through the command line and the sign-in screen.
